# myco-server Worker

Schema is applied at deploy time, never on the request path. Every member request reads the database schema version in the same query as the token lookup — before any token decision — and answers 503 when the version row is missing or is not the version this build was written against, so a deploy that skipped the schema step, or applied a stale one, fails closed rather than dropping events. `GET /health` reads no storage. A Worker bound to a validly migrated but wrong database answers 401 to every member (the schema matches, no tokens match); that binding error becomes visible in the owner status surface, not in ingest responses.

## Schema and migrations

The schema is a list of versioned steps in `src/db/schema.ts` (`SCHEMA_STEPS`); each step's last statement stamps its version into `schema_meta`. `npm run migrations:emit` renders one numbered file per step into `migrations/` (`0001_v1.sql`, `0002_v2.sql`, …); the directory is committed and a gate fails when it drifts from the source. `wrangler d1 migrations apply` applies the files it has not applied yet, tracked in the database's `d1_migrations` table, so a database created before the migrations runner (from the v1 `schema.sql`) takes `0001_v1.sql` as a no-op — every v1 statement is `IF NOT EXISTS` — and then `0002_v2.sql`. From step 2 on, steps are expand-only: no table or column is dropped or retyped, so an older Worker still running during a rollout reads a superset of what it expects.

```bash
npm run migrations:emit                                  # after editing src/db/schema.ts; commit migrations/
npm run migrations:apply                                 # local D1: wrangler d1 migrations apply myco-server --local
npm run migrations:apply:remote                          # remote D1: … --remote -c wrangler.deploy.toml
```

## First remote deploy

```bash
npx wrangler d1 create myco-server                       # once; render wrangler.toml into a gitignored wrangler.deploy.toml carrying the printed database_id
npx wrangler r2 bucket create myco-server-blobs          # once; the bucket name in both tomls
npm run migrations:apply:remote                          # brings the database to this build's schema version
npx wrangler deploy -c wrangler.deploy.toml
npm run token:mint -- <member_id> <machine_id>           # prints the members row and the member_credentials insert; apply both with wrangler d1 execute --remote
```

Order on every later deploy: `migrations:apply:remote` first, then `wrangler deploy`. The version check is strict equality, so between the two the old Worker answers 503 (retryable, with `retry-after`) to every member request and members spool until the new Worker is live; the new Worker refuses with 503 until the schema is at its version. `wrangler.deploy.toml` is derived, never hand-edited: `myco server config --out packages/myco-server/wrangler.deploy.toml` renders it from the committed configuration (embedded as `WRANGLER_TEMPLATE`, held byte-identical by `tests/server/wrangler-template-drift.test.ts`) plus this machine's deployment record — the account id, the custom-domain route, the D1 `database_id`, and the secrets-store binding. Re-render after any change to `wrangler.toml`; a binding added to the committed file reaches the deploy copy on the next render, and `wrangler deploy` prints the binding table to check against `Env`.

Local development: `npm run migrations:apply` (local D1) then `npm run dev`. `smoke.md` is the local smoke procedure and its last observed output.

## Members

A member is a person; a credential is one machine's membership of the Deployment, and the Project it acts on travels per request in `x-myco-project`. A machine joins by exchanging an enrollment authority at `POST /members/join`, or an operator mints a credential directly (`npm run token:mint`); either way the machine records it and capture starts.

```bash
MYCO_MEMBER_TOKEN=<token> myco member join https://myco-server.example \
  --project proj_… --token-env MYCO_MEMBER_TOKEN --provision claude-code
myco member status                                  # entry (token redacted), expiry, spool depth, last ack/refusal, latch
myco member drain                                   # deliver everything spooled, ignoring the offline latch
myco member refresh                                 # rotate early; hooks do it on their own inside the window
myco member leave [--purge]                         # forget the membership; --purge also drops the spool and the hooks
```

The token is read from stdin (`--token-stdin`) or from the named environment variable (`--token-env NAME`) — never from the command line, where it would be recorded in process listings and in lock metadata. Join verifies before it records and writes nothing to the server: the URL must be `https:`, the token must have the shape the server mints, and `GET /health` must answer.

`--provision <agent>` writes that agent's hooks for the project into the agent's member settings file (Claude Code: `.claude/settings.local.json`), rendered with the absolute path of this binary, `--credential registry`, and no PreToolUse hook — the member injects nothing before a tool call. Foreign hooks and the file's other keys are preserved, the 1.4 files (`.claude/settings.json`, `~/.claude/settings.json`) are never touched, and a target git does not already ignore is added to `.git/info/exclude`.

A sandbox is provisioned differently: it holds no registry, so it declares its credential in the environment.

```bash
claude -p "$TASK" \
  --setting-sources "" \
  --settings "$(myco settings --harness claude-code --project "$MYCO_PROJECT")" \
  --session-id "$RUN_ID" --output-format stream-json --verbose --include-hook-events
```

`myco settings` prints the same hook block with `--credential env`; the process must carry `MYCO_SERVER_URL`, `MYCO_MEMBER_TOKEN` and `MYCO_PROJECT` — all three or none. The settings carry no credential, so the printed block is safe to log. `--bare` removes every hook silently and must never appear in a provisioned launch.

The credential source is whatever the hook command declares and is never inferred: a `--credential registry` hook reads the registry entry for its project root and nothing from the environment, so a repository's own settings cannot redirect a laptop's capture. An env-sourced token is the orchestrator's and is never rotated — a successor's first use revokes its predecessor, which would lock out every other sandbox holding it.

Events a hook cannot deliver are spooled under `<MYCO_HOME>/member/spool/<project>/` and delivered by the next hook, or by `myco member drain`. A spool is never age-deleted while un-acknowledged: 30 days without an acknowledgement quarantines it, 60 days prunes the quarantined copy.

## Routes

`POST /events` — one capture event per request, `200 {persisted:true[, projected:true][, transcript:{size, segmentCount}]}` stored; `200 {persisted:true, duplicate:true}` a replay of an identical envelope; `200 {persisted:true, projected:false, code:'projection_conflict', reason}` stored but its projection did not apply; `200 {persisted:false, code, reason}` a terminal refusal of that request — never retry it (malformed or unknown-field envelope, unknown kind or payload field, a bound, size, depth or node cap, a `createdAt` more than 300000 ms ahead of the server clock, an event id already stored with a different envelope, an absent blob, a session, plan, transcript, or referenced prompt owned by another machine, a token without a machine identity, a transcript offset gap or overlap, write quota); `503 {persisted:false, code:'unavailable', reason:'unavailable'}` with `retry-after` a server-side failure — retry it. Every refusal and conflict carries `code`: one of `CLASSIFIERS` (`src/telemetry.ts`), the stable class a member acts on (`offset_gap`/`offset_overlap` re-slice, `quota` parks, everything else is terminal) — `reason` is text for people and is never matched. `401`/`429` before authentication; `401` to an authenticated member on a route this build does not serve; `409 {error:'protocol_version_unsupported', server_protocol, min_compat_member_protocol}` to an authenticated member whose `x-myco-protocol` header is missing, non-integer, or outside the window. Every response after authentication carries `x-myco-protocol: <server protocol>`; `/health` and `401` do not.

`POST /blobs/{sha256}` — content-addressed upload of a body whose lowercase hex SHA-256 is the path segment (anything else under `/blobs` is an unmatched path → 401). Headers: `content-type` (RFC 7231 `type/subtype[; parameter]`, ≤ 128 chars, canonicalized to lowercase; a bare `text/plain` is `text/plain; charset=utf-8`), `content-length` (required and at least 1; the pipeline never reads a stream body of unknown length), `x-myco-protocol`. The body streams straight into R2 under `<project_id>/<sha256>` with the digest as a store-side check. `200 {stored:true, duplicate:false, key, size, mediaType}` written; `200 {stored:true, duplicate:true, key, size, mediaType}` the project already holds that key (decided from the `blobs` row, uncharged; `mediaType` is the row's — the first uploader's — so a member presenting another type learns which one the row carries); `200 {stored:false, code, reason}` terminal (`media_type`, `empty_body`, `digest_mismatch`, `quota`, `content_length`, `blob_cap`); `503 {stored:false, code:'unavailable', reason:'unavailable'}` retry. The quota is reserved before any store write, against `member_credentials.bytes_written` — the same counter the CHECK enforces, so a token already at the ceiling from event traffic is refused before any byte reaches the store; an event's admission counts the token's live reservations in turn, so event traffic never takes the room an upload in flight holds (one admission expression, `withinQuota`, for every writer of the counter). Every path that returns without recording a row releases the reservation: a terminal refusal, a put that threw, a duplicate found at row insert, and a failed row batch alike. Every upload re-admits at reconcile — the reservation moves to the size the store recorded, is held for a fresh TTL, and the quota is re-checked against the room that remains — so a request whose room event traffic took while its body streamed is refused there, ahead of the charge; a terminal refusal after the bytes reached the store deletes an object this request put when no row claims it, so a refused upload leaves no orphan (an adopted object stays for the next uploader with room). A reservation outlives only a request that never returned; it stops counting against the quota at `BLOB_RESERVATION_TTL_MS` (15 min) and the token's next reservation deletes it. An object left in the store with no row is healed by the next upload of that key (object present, row absent → row inserted, charge kept, no second write); the ceiling holds against the size the store recorded, not only the length the caller declared.

`POST /tokens/refresh` — the presented token asks for its successor; the body is `{}`. Admitted only inside the refresh window, the last quarter of the TTL (`MEMBER_TOKEN_REFRESH_WINDOW_MS`, 1.75 days of 7): earlier, `200 {refreshed:false, code:'refresh_too_early', reason, refreshAfter}` where `refreshAfter` is the epoch ms at which the window opens — the member waits for it and never recomputes the window itself. Inside the window, `200 {refreshed:true, token, tokenId, expiresAt, refreshAfter}`: a new token for the same member and machine, answered once, expiring one TTL from now or at the lineage ceiling (`lineage_started_at + MEMBER_TOKEN_MAX_LINEAGE_MS`, 90 days from the operator-minted root), whichever is sooner; `refreshAfter` is the successor's own window start. A token already expiring at its ceiling answers `200 {refreshed:false, code:'lineage_expired', reason}` — re-provision (revoke the lineage, mint a new root). A predecessor holds at most one live successor (partial unique index `idx_member_credentials_live_successor`): a further refresh revokes the unused successor before inserting the next, so a lost response strands nobody — and whoever still holds that earlier successor is answered `401` without the protocol header, indistinguishable from an unknown token; this fires when a thief refreshed before the owner and equally when the owner refreshed twice (a lost response, then a retry) while a hook still holds the first answer, so a member writes the newest successor before any hook reads the registry. A successor issued late in the window of a lineage near its ceiling can carry `refreshAfter` earlier than now: the member treats that as eligible at once, refreshes, and is answered `lineage_expired` while the successor stays valid until its (ceiling-clamped) expiry — at most one window's worth. The predecessor stays live and keeps writing until the successor's **first authenticated use**, when the pipeline — right after authentication, ahead of the token limiter, on whatever route — runs one batch: the successor takes over the predecessor's held bytes (`bytes_written` plus its live blob reservations, the one `heldBytes` expression of the quota) and records `first_used_at`; the predecessor is revoked. That is the owner's detection signal when a thief refreshed first: the owner's token answers `401`. The route is exempt from the byte-quota pre-check, so a token at quota can rotate (its successor is at quota too). Refusals in this shape: a token without a machine identity (`no_machine_identity`), a non-JSON body (`parse`), a body that is not an object (`refused`, `body must be an object`), a body with a field (`unknown_field`); `503 {refreshed:false, code:'unavailable', reason:'unavailable'}` retry. The quota admission (`withinQuota`) also requires the charged token to be live, so a predecessor request that authenticated before the successor's first use and wrote after it stores nothing: its event answers `quota`, its upload fails at reconcile and deletes the object it put. A successor's row is inserted only while the presented token is still live at that instant (the one insert statement carries the predicate), so a lineage or single-token revoke landing mid-refresh mints nothing — a refresh that does not land changes nothing: the same predicate sits on the batch's revoke of the earlier unused successor, which therefore stays as it is — and the request answers `503 {refreshed:false, code:'unavailable', reason:'unavailable'}`; the member's next request meets the revoke as a plain `401`. Revoked and expired `member_credentials` rows are never swept — `events.token_id` resolves through them, so removing one makes the history it wrote unattributable — their number is bounded by `TOKEN_LIMIT` × the refresh window per member — and the operator sweep of `revoked_at < now − N` lands with Plan 4's token surfaces.

`POST /mcp` — the member tool surface: Streamable HTTP MCP (JSON-RPC 2.0 in the body, one JSON response per POST, no session) serving the seven §7.3 tools — `myco_search`, `myco_cortex`, `myco_sessions`, `myco_plans`, `myco_spores`, `myco_skills`, `myco_agent` — for the Project the request names, with `project_id` as a per-call pivot to another Project of the Deployment (an unknown one answers `{ok:false, error:'Project not found'}` and creates nothing). The definitions are the member side's (`packages/myco/src/tools/definitions.ts`) minus the retired Grove pivot, and results keep the member side's field names. Every (tool, op) is served or named as not yet served: a `not_served` error names the issue that delivers it (`myco_search` → #1027, Canopy → #920, notifications → #922, maintenance → #923; `myco_plans delete` is never offered — a Deployment keeps every plan). `myco_plans save` writes through the `plan` capture kind under the key a member hook derives for the same file (`uuidv5('plan', project, path)`), charged to the credential like any capture; a plan is a Project-shared row any member may update, attributed by `token_id`, keeping its creating session and machine. Spores a member records carry the built-in `user` agent and no session. The route's refusal shape is `answered`: a refusal is a JSON-RPC error envelope `{jsonrpc:'2.0', id:null, error:{code:-32000, message, data:{code}}}` — `400` for a terminal one (`no_project`, `no_machine_identity`, `parse`, …), `503` with `retry-after` for a retryable one (`unavailable`) — the statuses an MCP client surfaces to its caller; a tool failure the caller can act on is a JSON-RPC error on a `200` whose `data.code` is `invalid_input`, `unknown_tool`, `not_served`, or `tool_call_failed`. Telemetry: `mcp_tool {tool, op, status}`, `mcp_refused`, `mcp_error`. The member reaches it with `myco mcp --credential registry|env` (the stdio bridge an agent spawns) or `myco tool list|call … --credential registry|env`, both carrying the bearer, `x-myco-protocol`, and `x-myco-project`; the bridge never refreshes the credential, and an `env` credential may name plain `http://` only on the member's own loopback.

Retired 1.4.x routes (`/sessions/register`, `/sessions/unregister`, `/events/stop`, `/events/sync-transcript-prompts`, `/routed-capture/transcript`, `/routed-capture/plan`, `/context/subagent`) are declared in `RETIRED_ROUTES` with the kind that carries the same capture; a gate keeps them unserved and 401.

## Envelope and kinds

Envelope: `{eventId, sessionId, kind, createdAt, channel, producer:{adapter, version}, payload}` and nothing else — a field the server does not store is refused by name, never dropped. `eventId` and every member-minted logical id (`promptId`, `toolCallId`, `responseId`, `planKey`, `attachmentId`, `subagentId`, …) is a lowercase UUID; `transcriptId` is a UUID or `tx_` + 32 hex; `sessionId` is opaque, ≤ 128 chars. `producer` names the adapter and its version; both are identifiers ≤ 64 chars. An event id already stored in the project is a duplicate when the whole envelope (producer included) matches and a conflict otherwise.

`kind` is one of the closed catalogue in `src/ingest/kinds.ts` — `session.start`, `session.end`, `prompt`, `tool.use`, `tool.failure`, `response`, `plan`, `attachment`, `transcript.segment`, `compaction.pre`, `compaction.post`, `subagent.start`, `subagent.stop`, `stop.failure`, `task.completed`, `notification`, `error` — each with a closed payload schema and a bound on every field that lands in a typed column. Text that can exceed the 256 KiB payload cap (`prompt.text`, `response.text`, `plan.content`, `tool.use.input`/`output`, `compaction.*.summary`) travels either inline or as `blob` — the key of an uploaded blob — never both, never neither. The blob's media type is metadata the first uploader recorded; it is reported, never enforced.

Storage: every accepted event is one `events` row (raw log, with the producer, the spill key, and the payload byte count) plus its kind's projection — `sessions` (receipt from any event of the session, facts from `session.start`/`session.end`), `prompt_batches`, `tool_calls`, `responses`, `plans` (+ `tags`), `attachments`, `transcripts` + `transcript_segments`. Every admission precondition — the referenced blob exists, the transcript segment starts exactly at the held size, a continued session/plan/transcript is written by the machine that first wrote it — is a `WHERE` on the raw insert, so a refused event leaves no row and no charge; projections read from the raw row in the same batch, so an unstored event projects nothing and replaying the log re-derives the same tables. `prompt` and `plan` are upserted on a total order (client time `createdAt`, then the smaller event id): the highest-ranked event supplies every merged column — an absent prompt field included, so no other event fills it — and text is never rewritten (a differing text is `projected:false` with `reason:'prompt text differs from the stored prompt'`); a plan edit older than the stored one is applied where it converges (`created_at`) and answers `projected:true`; session facts come from the earliest `session.start` the same way. `transcript.segment` answers with the held `transcript.size`/`segmentCount` on every outcome, so a member resumes from the server's offset.

Write quota: `member_credentials.bytes_written` counts request body bytes of events the server stored for that token and blob bytes it wrote (reserved before the write, released on a terminal refusal), enforced by the `member_tokens_quota` CHECK inside the same transaction as the insert; refused, duplicate, conflicting, and oversized requests are not charged, and their ingress is bounded only by the token rate limit and the body cap. Changing `MEMBER_TOKEN_BYTE_QUOTA` changes the CHECK expression, so on a live database it is a schema step, not a redeploy.

Rate limits: `SOURCE_LIMIT` is charged only when a request ends without a member identity and never refuses an authenticated member; `TOKEN_LIMIT` bounds each token and is charged before the protocol window is checked, so a mis-versioned member is limited like any other. The Cloudflare rate-limit binding counts per edge server and is eventually consistent — a single-connection client is limited near the configured value, a client that fans out connections is not — so the byte quota, not the rate limit, is the bound on what a stolen token can store. A well-formed unknown token costs one indexed lookup before it is refused.

Tokens are compared by SHA-256 digest through a unique index; the digest is never a caller-steerable value. Telemetry carries classifiers, server-issued identifiers, and a digest prefix of the source identity — never a request body, path, address, or refusal text.

Member tokens: `npm run token:mint -- <member_id> <machine_id> [--print-token]` (a token without a machine identity is refused every write) prints the `INSERT OR IGNORE` for `members` and the `INSERT` for `member_credentials` on stdout — the row roots its own lineage (`lineage_root = id`, `lineage_started_at = now`, no predecessor); the raw token is printed to stderr only with `--print-token`. `npm run token:revoke -- <token_id> <actor_member_id>` prints the matching attributed `UPDATE`; `npm run token:revoke -- <any_id_in_the_chain> <actor_member_id> --lineage` prints the one `UPDATE` that revokes every live token of that lineage — predecessors and successors alike — which is the revocation for a stolen token, since a single-token revoke leaves its refreshed successors live. The scripts render the statements `issueMemberToken` / `revokeCredentialAsMember` / `revokeMemberLineage` execute, and every revocation names the member who applied it; see `BREAK-GLASS.md` for the emergency procedure.

## Dashboard

`ui/` is the server dashboard: a nested Vite + React package (own `package-lock.json`, installed on demand by `npm run build:ui` / `npm run check:ui`) building to `ui/dist`. Project scope rides the URL (`/p/<projectId>/…`); Deployment-wide pages are labelled server-wide. Appearance (theme, mode, font, density) is each viewer's own, held in the browser.

Serving is the platform's own shape on each target, with one rule shared between them — every path in `ownedPathPatterns()` (`src/routes.ts`: the live route prefixes and the retired 1.4 prefixes) is the server's; everything else is the shell:

- **Cloudflare** — Workers Static Assets, assets-first. `wrangler.toml`'s `[assets]` block names `ui/dist`, `single-page-application` not-found handling, and `run_worker_first` held equal to `ownedPathPatterns()` by `tests/myco-server/gates.test.ts`. No `ASSETS` binding: the Worker never fetches an asset itself. A GET to any unowned path answers the shell without a credential; any other method there answers 405 from the asset layer. The gitignored `wrangler.deploy.toml` carries the same block.
- **Self-hosted** — `platform/bun/static.ts` wraps the request handler when `MYCO_UI_DIR` names a build (the image sets `/app/ui`; the Dockerfile builds the UI in its own stage). Owned paths reach the server; other GET/HEAD requests answer a file or `index.html`; other methods answer 405. Static serving sits inside the loopback Host allowlist and ahead of source identity, so an asset request is never metered. A build directory without `index.html` refuses to start.

Sign-in is GitHub OAuth (`/auth/login`), and who may enter is a membership question answered on every request: the session's account must be linked to a live member. A member links their account once with `myco member link-github` (a one-time key, opened in the browser, confirmed on the `/link` page); `BREAK-GLASS.md` covers the first member of a fresh Deployment and changing an account. Sign-in answers once the Deployment holds its GitHub app credentials: `myco server github-app --url <deployment-url> [--org <name>]` registers the app on GitHub from a manifest (one click there), installs `GITHUB_CLIENT_ID`/`GITHUB_CLIENT_SECRET` on the Deployment — Worker secrets on Cloudflare, the bundle's `.env` and secret file on Compose — and verifies `/auth/login` sends visitors to GitHub and back. `SESSION_SECRET` is generated with the bundle on Compose and set as a Worker secret on Cloudflare.

Every Project has a display name: a Project the capture created takes the last path segment of the first session that named its origin, and the Projects page renames any Project (`PATCH /api/projects/{projectId}`). Sessions carry a title and a summary once they have ended: the request that ends a session schedules one provider call past its answer, using the Deployment's configured provider and its credential from Settings → Credentials (`anthropic`, `openai` or `openrouter` at their own endpoints; `openai-compatible`, `ollama` and `lmstudio` only at an endpoint named in `agent.provider.base_url`, reachable from the Deployment, with no credential — for `ollama` and `lmstudio` that is the server root, and `/v1` is added). Until then — and on a Deployment with no such provider — a session is labelled by the opening line of its first prompt.

Cut-over to schema v8 (the first release carrying member sign-in) on a Deployment that signed in as a configured owner: migrate the remote database, bind the owner's member to their GitHub account with `scripts/link-github.ts` (BREAK-GLASS.md), deploy, then delete the `OWNER_GITHUB_ID` secret — in that order, so nobody is locked out between steps. Every later member links with `myco member link-github`.

The dashboard's **Access** page (`/access`) administers members, invitations and runtimes; a project's **Access** page (`/p/<projectId>/access`) administers the external agents that may read it. Keys are shown once, every removal confirms what stops, and every act names who did it.

Local development: `cd ui && npm run dev` proxies `/api`, `/auth` and `/health` to `http://127.0.0.1:8787` (override with `MYCO_SERVER_URL`), rewriting the Host to the loopback literal the self-hosted server admits.

## Access

Membership is flat: every member manages members, invitations, runtimes and external agents, and every act names who did it.

- `GET /api/members` — members with whether an account is connected (never the account), and live runtimes. `POST /api/members/{memberId}/revoke` — ends the member and, in the same transaction, every live credential, unspent invitation and link key of theirs; refused `409 last_member` when it would leave no live linked member, `409 already_revoked`, `404` absent. A revoked member's credentials are refused at authentication on every route; machine claims stay, so their history stays theirs.
- `GET /api/enrollment` (live invitations), `POST /api/enrollment {memberId?, ttlMinutes?}` (a new member, or another runtime of an existing one; the key is answered once; at most a day), `POST /api/enrollment/{id}/revoke`.
- `GET /api/credentials?limit&cursor` (newest lineage first), `POST /api/credentials/{id}/revoke`, `GET /api/credentials/{id}/activity?limit&cursor` (what the credential wrote, across every Project).
- `GET|POST /api/projects/{projectId}/grants`, `POST …/grants/{grantId}/rotate`, `POST …/grants/{grantId}/revoke` — External Agent grants: a `mycoext_…` bearer, project-scoped by row and read-only, with no expiry; `last_used_at` moves at authentication at most once a minute. The `/mcp` surface that honours a grant is #921's.

There is no HTTP path that returns a member credential: a runtime is added by an invitation spent with `myco member join`; `scripts/mint-local.ts` remains break-glass.
