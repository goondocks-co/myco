# Deployment recovery artifacts

Operations > Create backup produces a manual JSONL export for additive restore, limited to 64 MiB of UTF-8 data. Its header counts describe the rows in the artifact. Rows are read in pages while the server continues accepting writes, so this export is not a transactionally consistent snapshot. It excludes object bytes, settings and sealed secrets. An export past the limit is refused before an artifact or index entry is written. Existing pinned artifacts remain intact. Download, restore preview and restore read a stored export only after checking it against its catalogue row. The stored bytes must match the recorded size; reading stops once the recorded size is exceeded. An export created at schema 41 or later must also match the SHA-256 recorded at its creation. A mismatch answers 409 `artifact_integrity`, and nothing is downloaded, previewed or applied. The export and its index entry are kept. An export catalogued before schema 41 has no recorded digest, so it is checked by size alone and a same-length change to it is not detected. Use the operator procedure below for a larger dataset or complete replacement recovery. An additive restore carries no object bytes, so it never registers a blob itself. Every blob row in the export must already be registered in the destination, under whatever stored object that destination holds for it; otherwise the whole export is refused with 409 `objects_missing` before any row is written. Each batch that writes rows naming a blob checks, in the same transaction, that the blob is still registered, so a concurrent deletion refuses the restore rather than leaving a reference to absent bytes.

`myco server backup --target local|cloudflare --to <directory>` captures the selected Deployment without applying migrations. A backup holds every object its snapshot names against deletion until its artifact completes: it opens a recovery hold on the source before the snapshot, and releases it once every byte is its own copy. While that hold is open the source records the deletions it decides and journals none of them, so storage grows by what deletion would have freed, and the Deployment keeps serving and keeps admitting its own automatic exports. An interrupted copy keeps the hold and resumes under it; `myco server recovery-hold --to <directory>` reads it, and `--abandon` gives it up, after which that directory can only be replaced by a new capture. A hold never lapses with age. The local target uses SQLite `VACUUM INTO`, including committed WAL data. The Cloudflare target uses the operator's existing Wrangler login and an explicitly bound D1 database; it exports ordinary tables and `sqlite_sequence`, reconstructs the source's indexes, views, triggers and external-content FTS indexes, and refuses schema drift. Cloudflare temporarily pauses database queries during its export. R2 objects stream through the operator process using an in-memory credential obtained with `wrangler auth token --json`; credential disk logging is disabled, redirects are refused and a rejected credential is refreshed at most once per object.

Both targets use one artifact writer. The directory contains:

- `myco.sqlite`: a closed database snapshot, checked for integrity, foreign keys and required captured-content references.
- `blobs/<project>/<sha256>`: every object registered in that snapshot, verified against its size and digest. The artifact path is the blob's logical identity. The source adapter reads each object from the stored name its own snapshot row registers (see Stored objects below), and a row whose project, digest or generation is outside the stored grammar refuses the snapshot.
- `blobs/backups/<filename>.jsonl`: every backup catalogued in that snapshot, including pinned backups. A backup created at schema 41 or later carries the SHA-256 of its stored bytes in its catalogue row, written when the backup was created; the copy must match that digest and its size, so a same-length substitute is refused and the attempt stays incomplete. A backup catalogued before schema 41 has no recorded digest. Its copy is checked by size only, and the command reports how many such backups the artifact holds. For every copy, the writer records the SHA-256 of the copied bytes in the manifest for resume and offline verification; for a backup without a recorded digest, that digest describes the bytes the source held at copy time, not the bytes it was created with.
- `recovery.json`: source target and identity, schema version, capture timestamps, database digest, blob totals, the Deployment's recorded configuration and the names of the independent credentials recovery needs.

The recorded configuration is public Deployment metadata, never a credential value. A native backup records its local record's `port`, `origin`, `sourceFrom`, `trustedHeader`, `trustedHops` and `fleet`. A hosted backup records the configuration its deployment record resolves to: the account and database ids, the database, Worker, blob store, recovery store, vector index and wrapping-secret names, and its secrets store id, URL and fleet where the record names them, together with the Worker version it ran. A hosted automatic staging records the same configuration without the version, read from the Deployment's own rendered `MYCO_RECOVERY_CONFIGURATION`, plus the member who started it. Every artifact names the same credentials: `SECRET_WRAP_KEY`, `SESSION_SECRET`, `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET`. An artifact from an earlier release may record less, and verification and copying read it unchanged; the credential report then says the artifact records none and names what recovery needs.

A hosted Deployment admits a new automatic export only when its rendered configuration agrees with every setting its runtime binds on its own: the export account and database, `MYCO_FLEET` and the origin of `MYCO_ORIGIN`. A Deployment deployed before the configuration was rendered, or one whose configuration is stale, answers `503 recovery_configuration_unavailable` and opens no hold; running `myco server update --target cloudflare` renders it again. An attempt already admitted still answers its status, its hold still settles, and a replayed admission of its token still answers that attempt.

"Back up every" schedules hosted recovery attempts. Set in hours, it drives one attempt once that interval has passed since the last attempt started, and nothing otherwise: nothing while it is unset, nothing while an attempt still advances, nothing on a Deployment that runs no producer, and nothing while this Deployment cannot admit one — a missing binding or rendered configuration is reported with the producer's own reason rather than attempted at every wake. The interval keeps no state of its own: the last attempt's own start is the cadence, so a duplicate wake admits nothing twice and a restart loses nothing. At most one attempt advances at a time, decided by the producer hold rather than by the schedule. A failed attempt waits the same interval as a completed one, which is the bound on retries, and its failure stays visible. The clock runs this on its own wake at every power state, including deep sleep, so a Deployment nobody has touched still takes its due attempt. A manual admission from the dashboard is independent of the interval, and neither starts an export from ordinary traffic.

The Deployment dashboard reports that state under Operations: whether automatic recovery is configured, unavailable or off; when the next attempt is due; what the last attempt did, including its failure; and what recovery data exists. It never calls a staging a recovery. A complete staging holds the export and every object its rows name, and becomes recoverable only when an operator materializes and verifies it into an artifact; until then the dashboard says exactly that. The small additive Backup export on the same page stays separate from complete recovery. A read that fails is reported as a failed read rather than as a Deployment without a producer.

Cloudflare provisioning and rendered bindings use the record's Worker, database, bucket, vector-index and wrapping-secret names. Existing records that omit `vectorIndexName` or `wrapKeySecretName` retain the default names. A recovery record can name separate resources; the record must also name the recovery destination's URL rather than the original live route. Choosing those resources does not copy data, recover credentials or rebuild their contents.

The manifest advances from `snapshot` to `content` to `complete`. A failed copy stays incomplete. Running the same command against the same source and directory resumes the saved snapshot and verifies existing bytes before reusing them. A completed artifact is verified without refreshing its contents; use a new directory for another recovery point. A different source or an unrelated nonempty directory is refused. One process holds the destination lock at a time.

New artifacts use `myco-recovery/2` and include digests for catalogued backup objects. Existing `myco-recovery/1` artifacts remain readable and retain their original coverage. Verification reports when a legacy artifact's database contains backups whose object bytes are outside that coverage; use a new destination to capture them. It does not silently upgrade or modify a completed legacy artifact. Backup catalog rows alone do not preserve the downloadable artifacts.

`complete` means the data artifact passed verification. It does not establish that independent credentials exist, that an external vector index has been rebuilt, or that a replacement Deployment works. Keep the original wrapping key, session secret and GitHub application credentials in separate secure recovery storage. Wrangler credentials stay on the operator's machine and are not copied into the artifact or Deployment. The database itself contains private project data and encrypted settings; treat the directory as private.

Native recovery writes into a fresh `MYCO_HOME`:

```sh
MYCO_HOME=/path/to/fresh-home myco server restore --target local \
  --from /path/to/recovery-artifact --secrets-from /path/to/independent-secrets.env \
  --port 8787 --yes
```

The separate credentials file uses `NAME=value` lines for `SECRET_WRAP_KEY`, `SESSION_SECRET`, `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET`. Keep it outside the data artifact. Recovery verifies that the wrapping key opens every stored credential; it never generates a replacement key. An existing destination, incomplete artifact, missing backup coverage or unreadable credentials is refused. Data copies use the common artifact owner, and configuration is published only with the verified volume. A failed unpublished attempt can be retried; it leaves the source intact. A process killed during staging can leave a private `.local-restore-*` directory beside the destination; the next attempt uses a fresh staging directory.

If the original sign-in credentials are unavailable, add `--new-signin` for hosted recovery. This explicit choice requires only `SECRET_WRAP_KEY` in the independent file. It generates a new destination session secret and omits the old GitHub application credentials, even if they are present in the file. The original wrapping key is still required to open saved encrypted settings. Source sign-in and source credentials are unchanged. The destination's owner sign-in remains unavailable until you run `myco server github-app --target cloudflare` for its URL using the same recovery `MYCO_HOME`. A hosted retry must use the same sign-in choice as its saved journal. Dashboard/OAuth acceptance remains pending until that setup succeeds. Native recovery requires all four credentials. The native GitHub App setup command is `myco server github-app --target local`; stop the native server before running it and start it again afterward.

The recovered native endpoint uses loopback and the selected port. A recorded fleet is carried into the published record, and the command says so; an artifact that records no fleet leaves the source fleet unknown, and the Deployment is published without one, so dispatch applies no fleet bound. A recorded fleet that is not a whole number of runtimes refuses the restore. The recorded `origin`, `sourceFrom`, `trustedHeader` and `trustedHops` are not applied: the restored Deployment keeps the native defaults, and configuring them for its new host remains the operator's. `recovered-from.json` records the source snapshot, whose database digest predates any derived-state reset or startup migrations. Native vectors remain in their copied SQLite table. Hosted snapshots have external vectors, so their readiness receipts and indexing cursors are reset through the embedding owner. The reset preserves knowledge and source revisions. On startup, native embedding work uses the configured provider through the Deployment's queue and wake registry. Readiness must be verified from rebuilt receipts and semantic results; a completed recovery command only establishes the data volume. Starting the destination is separate: `MYCO_HOME=/path/to/fresh-home myco server run --target local` applies pending migrations and starts serving. Configure the GitHub application's callback for the recovered endpoint before testing owner sign-in.

Native lifecycle mutations, the serving process and an operator backup share one volume lease, in two modes. Every mutation of what the volume is — migrations, the record, secrets, owner setup and recovery — takes it exclusively. A serving process and an operator backup take it shared, so a Deployment keeps serving while a backup copies it, and no mutation can replace the volume under either. One process serves a volume at a time, which a second lock decides. A start whose volume is behind the binary must migrate it, so it exchanges its shared lease for the exclusive one, and is refused while a backup or another operation holds the volume: the start says so and the backup keeps its snapshot. Because that exchange holds nothing for an instant, the volume's identity is compared before the migration and again before serving, and a volume that changed refuses the start. Configuration and secrets are read from the volume the lease accepted. A lease is the kernel's, so a process that dies releases it; the hold a backup took lives in the database and outlives its process. Recovery refuses an existing directory even when no process holds it.

Hosted recovery also requires a fresh `MYCO_HOME`, the operator's Wrangler login and independently held credentials:

```sh
MYCO_HOME=/path/to/fresh-home myco server restore --target cloudflare \
  --from /path/to/recovery-artifact --secrets-from /path/to/independent-secrets.env \
  --account-id <cloudflare-account-id> --yes
```

The command provisions uniquely named D1, R2, Vectorize and Worker resources. It installs the original wrapping key under a new secret name in the account's Secrets Store. It preserves the source URL and resources; the replacement uses its own `workers.dev` URL. A recorded fleet is carried and reported; an artifact that records none leaves the source fleet unknown, and the replacement is published without one. Configure the GitHub application's callback for the replacement URL before testing sign-in, and attach workers to that endpoint explicitly.

The database import preserves typed values, rowids, sequence high-water marks and reconstructed FTS indexes. Individual SQL statements are bounded for D1. A completion fingerprint distinguishes a saved import from an unrelated or incomplete destination. The migration ledger records the schema steps already present in the snapshot before the bundled pending migrations run. An unrelated nonempty database is refused. Existing destination objects must match their expected size and digest; uploads are read back and checked. The operator upload path currently refuses objects larger than 300 MB.

The replacement has a fresh external vector index, so the private database copy resets embedding receipts and cursors through the embedding owner. Knowledge records and source revisions remain intact. The Worker initially returns 503 with no data bindings or scheduled work while credentials are installed. The real application is deployed after database and object verification; the canonical operator record is published after that deploy returns its version.

Hosted lifecycle, record and staging mutations share one operator lease. `server/cloudflare/recovery.json` records the source fingerprint and confirmed resources without secret values. An interrupted data import or object transfer can resume against those same resources. Confirmed vector-index creation is recorded before preparing its asynchronous filters; a filter failure or visibility timeout can be retried on the same index. A resource-creation or final-publication call whose result is unknown leaves a named pending operation and refuses automatic retry. Reconcile that specific replacement resource with the provider before changing the journal; do not delete or adopt source resources. There is no automated cleanup of partially provisioned resources. A published destination refuses another restore.

Compose retains its existing procedure. Owner-dashboard additive artifact restore uses the server backup core and is a separate operation. A successful restore command does not establish owner sign-in, attached-worker execution, semantic-search readiness or sustained operation. Acceptance still requires source-preserving recovery on the required targets, exact records and blob bytes, independent credential recovery and actual UI/MCP reads before an artifact can authorize a migration-bearing update.

## Stored objects

A blob row is keyed by its content, `(project_id, key)`. The stored object it registered carries the row's generation as well: `<project>/<sha256>~<generation>`, a UUID the upload's own reservation minted before any byte moved. Rows registered before schema 42 have no generation and name `<project>/<sha256>`. Nothing writes that name now: uploads never adopt bytes already in the store, and both restore paths name every restored blob under one fresh restore generation.

An upload stores its bytes only under its own generation and registers them only while its reservation is live, consuming the reservation in the same transaction. A refusal, an error, an unknown store write or an expired reservation consumes the reservation and journals that generation's bytes for deletion instead. An upload whose reservation expired or was consumed first is answered as retryable, and the retry stores under a fresh generation.

No code deletes stored bytes directly. Session deletion, transcript retention, the orphan sweep and backup retention record what they may have freed as release candidates, in the transaction that removes the rows naming them, and a release decision journals the exact stored object each unreferenced candidate registered. The clock-owned `object-release-drain` job is the only store deleter. It removes a journal row only after the store acknowledges the delete; a delete that fails, times out or loses its answer stays journaled and is issued again. Because stored names are never reused, a late or repeated delete can only remove bytes already released. The drain runs from the Deployment's own clock (the hosted clock object, or the native wake loop), never from an owner's wake request, and not while a recovery export has the database paused.

A hosted recovery export opens a recovery hold before the attempt is admitted, and an operator backup opens one of its own. A hold names its holder, at most one of each holder is open, and releases defer while either is open: an operator backup never stops this Deployment admitting an export, and an export never stops a backup. While a hold is open, releases keep their candidates recorded and journal nothing registered. The `recovery-hold-release` job settles the producer's hold only, and releases it when the producer answers that its attempt advances no further, or that no attempt carries it (the token is then retired, and admission refuses it). There is no interval after which a hold lapses. Recorded candidates survive the hold, later holds and the orphan-sweep window; after release they are judged again against the rows, and backups against the retention policy then in force.

An operator backup's hold is the backup's own: the producer is never asked about it, and schema step 43 makes its one transition total in the database. It is inserted open, the only change it accepts is its own release to a completion or an abandonment, and a released hold accepts no further change. A writer that predates the step releases a hold with a statement that sets no holder, so that statement aborts on an operator hold, and a Deployment still serving the earlier release keeps deferring its deletions, fails that job's pass and admits nothing while the hold is open. An owner status answer reports the open hold, and reports it as unknown rather than absent when the Deployment's database cannot be read; the attempt's own progress comes from the producer and is never lost to that read.

A destination records the token of the hold it takes before the hold exists, and the identity the source answered with once it is open, both durably. That identity is the Deployment and schema version the source answered in the same statement as the hold; a source that answers a hold without naming both refuses the backup rather than being bound to a placeholder. No snapshot is captured before that binding exists, so a resume always has something to compare: the recorded identity decides before anything is opened and again on the answer the acquisition gives, so a source replaced while its hold was gone refuses the resume instead of being captured under the first receipt, and the receipt is never rewritten to fit a replacement. A destination whose hold is released, absent or another holder's refuses rather than reopening one over a saved snapshot. Each hold is also attested by the source's own open hold naming this destination's token, and the snapshot's own Deployment and schema version must be the ones the hold admitted, so substituted bytes are refused however the source answers at release time. A write whose answer is lost is settled by asking about the same token, never by taking a second hold; each of those statements is bounded — a hosted one kills its provider command, a native one takes a non-blocking volume lease — and an unanswered one is reported as unknown rather than as an absent or released hold. A completed artifact stays verifiable, and a release whose answer is lost is reported as unresolved and reconciled by running the command again.

Restore resets the destination's copy of this lifecycle on the prepared database, whether or not embeddings are rebuilt: holds, journal, upload reservations and backup candidates from the source are cleared, and blob candidates are kept to be judged again. The prepared copy is first brought to the bundled schema by the migration applier, so a schema-41 artifact is restored and started without applying any step twice.

Schema step 42 also fences writers that predate it, from the moment the step commits: a `blobs` row cannot be inserted without a generation, and a row with a generation cannot be deleted unless its exact stored object is journaled in the same transaction. A previous-version upload therefore fails retryably instead of registering a legacy-named row, and a previous-version deletion or sweep cannot remove a row registered under a generation. The fence has limits, and an upgrade must not assume more: it does not protect objects stored under a pre-step-42 `<project>/<key>` name from a previous-version deleter still running, it does not stop a previous-version recovery producer, and it establishes nothing about when previous-version execution has ended.

Open under #1316: a store write that lands after its acknowledged clean-up leaves bytes that no row, journal entry or reservation names. They are never read and never charged, and no store walk reclaims them in this release. Previous-version Worker requests still running after an upgrade keep their earlier behaviour until they end; see the deployment coexistence gate before relying on these guarantees during an upgrade.
