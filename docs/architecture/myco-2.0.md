# Myco 2.0 — Canonical Architecture and Feature-Preservation Ledger

> **TL;DR.** Myco 2.0 is one feature-complete server product with two front doors — a single Bun binary and a Cloudflare Worker — plus a machine-side member install of the binary, hooks and plugins. Neither front door runs harnesses: task runs happen on workers that attach from wherever harnesses are logged in. This document is the single current architecture record for the whole 2.0 release and the completeness ledger that gives every 1.4 surface an explicit KEEP / REPLACE / DROP disposition and an owning surface. It is machine-enforced by `tests/meta/feature-ledger-completeness.test.ts`.

**Feature Preservation.** Replacing local daemon and server infrastructure does not change Myco's major feature set. ## 3. Destination architecture

The settled model. Terms are defined in [`CONTEXT.md`](../../CONTEXT.md), which is the canonical glossary; this section states the structure, not the definitions.

### 3.1 Deployment and Project

A **Deployment** is one physical server/data authority. It replaces **both** Grove and Team as the isolation and infrastructure boundary. A Deployment contains many Projects. Separate personal, client, or security boundaries require separate Deployments.

A **Project** is the shared body of collective intelligence for equivalent Git checkouts. Checkouts with the same portable Project ID or normalized Git remote contribute to the same Project. There is no separate project-sharing product — sharing is inherent in Deployment membership.

**Project Binding** associates a local Git project with an explicit Deployment or the Default Deployment. **Project Resolution** applies in order: portable Project ID → normalized Git remote → server-assigned identity. Different Git remotes do not auto-merge; rare duplicates are corrected by server-side **Project Reassignment** followed by normal reprocessing.

### 3.2 Membership and runtime identity

Server Provisioning creates **Enrollment Authority**. Joining exchanges it for an individually attributable **Member Credential** — the enrollment secret is never the credential used for ordinary requests.

**Membership is Deployment-wide with owner, admin and member authority.** Every live member can use processed intelligence across every Project in the Deployment; raw capture remains private to its uploader. `members.role` stores `admin` or `member`; the revisioned `deployment_ownership` singleton identifies one admin-capable human owner. The authorization declarations and one engine admit every HTTP route and MCP operation. Only the owner grants or revokes admin authority and transfers ownership. Admins retain ordinary administration, and members read roles without changing them. Transfers and role changes are atomic, revisioned and actor-attributed; the old owner remains an admin. The active owner and last linked human admin cannot be removed or demoted. Stopping a runtime credential leaves its linked GitHub dashboard membership available for recovery.

**A Member Credential rotates; it never ages out** (#1417, decided 2026-09-26). Each token lives seven days and the member rotates it silently in the last quarter of that life, so a copied token dies within a week unless its holder keeps refreshing it. Theft is answered by **replay detection** — a superseded token issued within the 90-day idle window that asks to rotate means a second holder rotated the lineage, so the Deployment revokes every live row of it, both holders' (`revoked_by = 'lineage-replay'`), and the owner's member, whose refused capture forces that rotation, says the credential was used from two places; elsewhere a superseded token is recorded as `lineage_replayed` and revokes nothing, since a racing hook or a stale MCP bridge presents one legitimately — and by **owner revocation** from the dashboard, whose Stop ends the credential's whole lineage — not by a fixed re-login age: the 90-day lineage ceiling is gone, and a machine in daily use never re-joins. Only **prolonged inactivity** does: a token that lapsed offline still rotates while its lineage refreshed within the last 90 days (`MEMBER_LINEAGE_IDLE_MS`, measured from the presented token's `issued_at`, the last successful refresh or the join), and a machine silent longer than that is refused with `lineage_expired` — the code every member build already treats as final — and shows the notice to ask an admin for an invite and run `myco login`. **An env-sourced credential does not rotate** (#1420, decided 2026-09-28). The issuer marks it at mint (`member_credentials.rotates = 0`, schema step 52; `token:mint` requires `--rotating` or `--non-rotating`, and every run credential is minted non-rotating), never from runtime claims. Every member route that mints an authority able to outlive it (`mintsAuthority` in the route table) refuses it with `non_rotating`, live or lapsed: `/tokens/refresh`, as it refuses a run credential, so a copy handed to many sandboxes, or taken by a second holder, can mint no successor and so can fork no lineage; `/members/link-github`, whose dashboard session could mint an invitation and so a rotating runtime (and which, since #1448, answers any member credential only while no admin is linked); and `/worker/claim` and `/worker/repository`, which answer a run credential, a provider key and a repository credential. `token:mint --non-rotating` creates its member as a plain member and never mints for one that administers the Deployment. It lives out its seven-day TTL or a Stop, and the orchestrator renews by minting. The member holding it from the environment stays passive on a `401`; a registry that holds one records the refusal once and never dials the refresh route for it again, with no terminal state.

**Linking a GitHub account is bootstrap, then admin** (#1448, decided 2026-09-28). A member credential links its own member's GitHub account (`POST /members/link-github`, `myco member link-github`) only when that member is an admin and the Deployment has no live admin with a GitHub account linked — the first sign-in on a fresh Deployment; the self-hosted first-owner setup mints the same kind of key. Bootstrap ends once: from the first bind on, removing a member refuses to leave the Deployment without a live linked admin (`last_admin`: "This is the only admin who can sign in; add or link another admin first."), only the owner may demote another admin, and no membership mutation removes the active owner or last linked human admin or clears an account, and the break-glass `scripts/link-github.ts` only replaces an account with another. Once any admin is linked, the route answers every member credential `link_requires_admin` and writes no key, so a member token alone never chooses which account the dashboard's SSO accepts. From then on a signed-in admin links a member from the dashboard (Members → Connect GitHub, `POST /api/members/{memberId}/link-github`, dashboard session only): it creates a one-time key the member opens, and their GitHub sign-in on `/link` proves the account. `identity_link_authorities.issued_by` (schema step 53) records which: NULL for a member's own key, the admin's member id otherwise. One SQL predicate states the rule — a NULL issuer for an admin member while no linked admin exists, an admin issuer while it is still a live, linked admin — and both the key's insert and the account's bind carry it in their own write, so a key minted during bootstrap binds nothing after it, an admin's key dies with that admin's standing, and of two first sign-ins at once only one binds: every bootstrap bind links an admin, and the first one ends bootstrap for the rest. Cloudflare and self-hosted serve the one route table, so the rule is the same on both (`tests/parity/scenarios/github-link.ts`). Changing a linked account stays break-glass (`scripts/link-github.ts`).

**Every dashboard route declares who it admits.** Session routes declare `admin`, `member`, or `account` admission and an authorization action with its resource resolver. The pipeline applies the declared authority and the shared authorization engine before reading a write body or invoking the handler. Owner-only actions require the singleton's current live admin; until explicit owner selection, they answer `owner_pending`. Non-owner admins cannot transfer ownership, change roles, grant admin authority, or revoke an admin. Ordinary administration remains available to admins, and every live member can read processed project intelligence and the member directory. Credential reads and writes resolve their member and active-owner protection through the same engine and conditional write guard. The dashboard renders the role and ownership authority returned by `/auth/me`; hiding a control does not replace server admission. Route declarations, refusal-before-write gates and native/D1 parity cover the common policy.

Human member identity is distinct from machine, runtime, or coding-agent metadata. A persistent developer machine and an ephemeral **Sandbox Runtime** act as the **same member with the same capabilities**. Independently hosted cloud agents (e.g. a Copilot review agent) are **not members** and receive project-scoped read-only **External Agent Access**.

> The exact enrollment, member identity, approval, recovery, and step-up mechanism is an open research decision owned by **#907**. The constraints above are settled; the mechanism is not.

### 3.3 One server product, two front doors

The Cloudflare Worker and the self-hosted binary implement **one common server contract and shared core** with platform-specific adapters — not divergent products. Both are storage + MCP + ingest + scheduler. **Neither runs harnesses** (plan §2.6).

| | Cloudflare Deployment (**W**) | Self-hosted Deployment (**C**) |
|---|---|---|
| API + assets | Worker with static assets | Single Bun binary — the same one a member installs, serving `myco server run`; both dashboards travel inside it as generated asset modules, so it mounts no build directory. A container image is packaging, not a requirement |
| Relational store | D1 | Embedded SQLite |
| Blob store | R2 | Local volume |
| Vector store | Vectorize | Local SQLite vector adapter |
| Wake / schedule | `DeploymentClock` Durable Object alarm + cron floor | In-process scheduler |
| Secret wrapping key | Secrets Store binding | Env or file (`secrets.env` idiom) |
| Harness | The Deployment runs no coding harness; an attached worker serves the four prompted outcomes. Its embedding-only runtime uses the authenticated run routes in bounded response work; the wake invocation awaits the work it starts | Explicitly enrolled runners attach over the Deployment's own HTTP surface using a runner credential. `myco server run` serves without an agent executor, including after upgrade. Existing standalone member-credential executors remain legacy until explicitly retired. A dispatch is never refused for want of a harness: it queues, and an operator reads the wait on the run. Two tasks keep the push-launch seam until the sweep — `embedding-reconcile`, whose surface is a server-side step loop rather than MCP, and `container-smoke`, the containerized runtime's own proof. Native `embedding-reconcile` binds an in-process runner over the same authenticated run routes and bounded step loop; its task allowlist admits no container-only task, and stopping the Deployment drains this runner before releasing its volume |
| Durable storage | Platform-managed | Local volume beside the binary |
| Native storage artifacts | Platform-managed | Carried in the binary: an extension-enabled SQLite library and the `vec0` extension, registered before the first connection. A host lookup remains for a checkout and a container image |
| Lifecycle | `myco server create\|update\|rollback\|status\|destroy --target cloudflare`, needing Node and a wrangler login on the operator's machine and neither on the Deployment | `myco server create\|run\|install\|uninstall\|status\|update\|destroy --target local`, with a per-user service (launchd, systemd `--user`, Task Scheduler) running `myco server run` at login |

The `HarnessContainer` Durable Object and the `[[containers]]` block are gone, retired by a `deleted_classes` migration (plan §2.6, §4 D2); `DeploymentClock` stays. Containers are a paid-plan surface, so removing them is what puts the stack on the free tier. Provisioning is one verb over a worker bundle the binary carries — no Docker, no source checkout — with Node and Wrangler an **operator-machine** prerequisite for that verb alone, never on a member or worker host.

Shared behavior belongs in the common core; target-specific infrastructure, storage, wake, TLS/proxy, backup, and observability behavior belongs in adapters. **Neither target may silently lose a feature because the other implemented it first.** A ledger row naming a capability without its per-target mechanism is how one target never gets it. [Deployment recovery artifacts](deployment-recovery.md) defines the operator backup format, completeness checks and remaining replacement-recovery boundary.

Both front doors pass the same ingest parity and eval suites before release (§8).

### 3.3.1 Deployment-held secrets (#961, approved 2026-08-24)

Secrets divide by **who reads the value back**, and only one of the four classes is a secrets-storage problem the Deployment shares with a laptop.

| Class | Examples | Stored as |
|---|---|---|
| **1a** mint-and-verify | member credentials, enrollment authorities | **Digest only.** Never retrievable — this is what makes a backfilled credential unresurrectable (#912) |
| **1b** mint-and-display | MCP access tokens, team keys | Retrievable: a member pastes the value into an external Cloud Agent |
| **2** third-party, in-process | `GITHUB_TOKEN` | Retrievable: our own code signs API calls with it |
| **3** third-party, subprocess | `ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, OpenAI/OpenRouter | Retrievable, and must reach a harness process env under the provider SDKs' own names |

Classes 1b, 2 and 3 share **one** `SecretStore` port and one implementation; 1a keeps the digest path and must never route through it.

**Ciphertext lives in the store; the wrapping key does not.** Values are AES-256-GCM through Web Crypto — native on both targets, so no dependency is added — with a fresh IV per write and the secret's own name as AAD, so a ciphertext moved between slots fails to decrypt rather than returning the wrong credential. `key_version` is carried from the first migration so re-wrapping is a migration and not an outage.

The reason is our own design rather than a generic precaution: **direct store access is a deliberate, documented capability.** `BREAK-GLASS.md` prescribes `wrangler d1 execute --remote`, and #907 settled infrastructure control as proof of authority — it is the only recovery that survives losing every credential. Plaintext third-party credentials in that store would make every break-glass operation, operator query and leaked account token a disclosure of every provider key at once. The platform encrypts the store at rest, which defends the disk and not the access the runbook prescribes.

A member's own `secrets.env` is unchanged and out of scope: a `0600` file on a single-user machine is reachable by the person it belongs to, which is a different threat from a shared Deployment store.

**No managed secrets dependency is taken.** Vault-class products centre on dynamic short-lived credentials, and LLM providers issue only long-lived bearer keys — the main thing they buy does not apply to the dominant class — while every one of them would require a self-hosted operator to run infrastructure to use Myco at all.

### 3.4 Member Installation, plugins, and tenancy

The machine-side product contains the `myco` binary, hooks, spool, local registry/configuration, and optional runner mode. Capture is hook-invoked and write-ahead per the member seam (#901). Login, member join/provision, and native `server run` install or start no executor. Agent execution requires the machine owner's explicit runner enrollment (`myco runner register <host>`) and service installation (`myco runner install`), or foreground `runner run`.

A runner service uses the enrolled runner record under its own `MYCO_HOME`, independent of membership and capture, through the per-user adapters in `runner/service.ts` and `server/service.ts`: LaunchAgent on macOS, systemd user unit on Linux, logon task on Windows. `member leave` preserves executor services; `runner uninstall` stops/removes only its local service and retains the Deployment identity and capture. Global `myco remove` stops this home's executor services before removing install state; an unconfirmed stop aborts removal. Foreign-home runner units remain owned by their own home.

Existing member-credential worker services remain installed and are reported as **legacy worker — uses member credential**. `myco worker` is the compatibility entry point for runner operations and retained legacy-service management. Repeated legacy installation preserves active work; explicitly uninstall the legacy service after its active run finishes before starting the runner. A legacy unit cannot prove its Deployment identity across arbitrary origin aliases, so runner startup refuses while any legacy unit or foreground executor without an authenticated Deployment lock remains on the machine. New executors share machine-wide locks for canonical origins, recorded native aliases, historical URL keys and the authenticated Deployment identity. Runner authentication never falls back to a member credential. Owner/admin legacy inventory retains last contact and valid leases, including offline workers until revocation.


**Distribution splits in two** (plan §2.7):

- **Plugins** carry no binary — 82 MB against a 256 MiB cap, and no post-install scripts. **One bundle directory carries every client's manifest over one skills tree** (`plugins/myco/`, generated; the marketplace manifest is `.claude-plugin/marketplace.json` at the repository root, where every client that reads a git repo looks): an **Agent Plugins 1.0** manifest covering Codex, Cursor, VS Code Copilot and Antigravity, plus Claude Code's, Cursor's and Codex's own manifest beside it. **OpenCode, Pi and Cline take native in-process plugins that make no HTTP call of their own** (#1157): each translates its harness's lifecycle onto the binary's hook verbs, so the credential, the write-ahead spool, the server-held offset and the refusal codes have one implementation rather than four. OpenCode and Cline keep no append-only transcript — one stores a session as a file per message and per part, the other rewrites whole documents in place, and neither carries a byte offset a delta can ship against — so their plugin writes one under the member home and Myco's retention ages it; Pi writes its own and Myco only reads it. Cline is served at the reduced tier through that same plugin, which resolves D4: keeping it removes a hand-maintained copy of the transport rather than adding one. Each client declares the Deployment URL and credential through its own config prompt (Claude Code `userConfig`, Cursor `variables`, VS Code `inputs`, Codex `[plugins.*.mcp_servers.*]`), emitted from one spec so the five prompts cannot drift. **The marketplace bundle ships no hook**: a hook command is the binary's absolute path, resolved on the target machine at install time, which is why capture arrives with the installer and why the native plugins above are installer-written rather than bundle-carried. **Plugin alone = skills + MCP tools on every harness**, authenticated by an External Agent grant — the one credential shape the pipeline admits without a machine identity, a protocol header or a Project header, none of which a plugin can supply, and whose surface (#1149) is already the six tools a symbiont reads. It reaches one Project, it is minted by an owner, and it expires (90 days by default), all three stated in the plugin's own README and in the setup skill.
- **The installer** (POSIX `sh`, PowerShell) places the binary and writes capture hooks with absolute paths. It adds capture, plan capture, import and the worker, the last as a login service that restarts on failure.

**The retained hook set** (plan §2.2, **landed in #1155**). For a harness the Deployment parses — Claude Code, Codex, Cursor, and the native-plugin harnesses — the hooks do three jobs and write no turn row: `SessionStart` registers the session with the hook-exclusive facts (git branch, parent session and reason) and injects; turn end (`Stop`, `SessionEnd`, `session.idle`) ships the transcript delta past the Deployment-held offset, the subagent transcripts written beside the session under their own identity and role, and the plan files the turn wrote — an `Edit` record carries only a diff, so the hook finds the write in the delta and reads the file; `UserPromptSubmit` injects, and ships a plan a person pasted inside a tag envelope under a key the parse never derives; `SubagentStart` injects into the delegated agent. Claude Code's re-injection after a compaction rides `SessionStart` with the `compact` matcher, which advances the compaction ordinal itself — its `PostCompact` output is discarded by the harness and cannot inject. Cursor's prompt hook can only block, so it is not wired; Cursor keeps `postToolUse` and `postToolUseFailure`, the one source of its tool calls, and its session block gets a second chance there. The member kinds on the wire are therefore `session.start`, `session.end`, `transcript.segment` and `plan`, plus `tool.use` and `tool.failure` from a harness whose transcript declares `no_tool_results`. Which side writes the turn rows is one manifest declaration, `turnRowSource`, held equal to the presence of a server parser by `tests/meta/parser-manifest-parity.test.ts`; a harness the Deployment does not parse (Copilot, Antigravity, Windsurf) keeps its hooks as the writer until a parser lands or the sweep (#1170) retires it. Transcript identity is (machine, path, inode, head digest): a file truncated and rewritten in place keeps its path and inode and changes only its head, so it ships again as a transcript of its own, and a pointer minted before the file had a digest keeps its id. The write-ahead spool stays, drained on the next hook with backoff, and a drain that delivers everything prunes the state of sessions delivered long ago.

**Sandbox images ship the CLI, hooks and a join code** — no resident service, symbionts fixed at build time, the container short-lived. The join code (URL + credential in the environment) is exchanged at first contact for a member credential bound to the Project resolved from the repo remote.

**Tenancy is a tool parameter, not a transport** (plan §3 D1). Every Myco tool accepts `project` — a git remote or a project id — and the server resolves remote → project by the Project Resolution rule (§3.1). Reads default to the member's bound projects; **writes require an explicit project**. Session-start injection tells the agent its project id where hooks are installed, and the `myco` skill tells it to pass the repo remote where they are not. The 1.4 CLI transport for tenancy-blind harnesses retires; `myco tool call` remains as a CLI surface onto the same server code path.

Home-pin creation during join is exclusive for both project and machine pins. A pin rejected by the trust reader is still an existing file: join preserves its bytes, target and permissions, reports that it could not write the pin, and retains the recorded membership. Pin contents and permissions are written through one open file descriptor.

Member provisioning reconciles hooks and the MCP entry independently. An unchanged hook file does not suppress a missing or changed MCP entry, and the join command reports an unchanged registration as such. `myco member join --provision <agent>` and `myco member provision <agent>` share one provisioning step (`provisionAgent`, `cli/member.ts`); `provision` runs it from the membership already recorded for the project; no token is supplied or changed.

**Member provisioning is global by default.** The selected project supplies the recorded membership; it does not select a project-local installation. Hooks, plugins and MCP entries use the agent's user-wide targets. Codex uses `~/.codex/hooks.json` and `~/.codex/config.toml`; Claude Code uses `~/.claude/settings.json` for hooks and `~/.claude.json` for MCP. After writing the global replacement, provisioning removes this project's member hook and MCP entries through `SymbiontInstaller`, preserving unrelated configuration. Leaving a project preserves the global integrations used by other projects.

An authenticated member can initialize MCP and list tools without a Project header. Every tool call on that connection names an existing Project through `project`; no default Project is inferred and discovery creates no Project. A connection with a valid Project header retains its default for reads. Writes always name their Project. Run and grant credentials retain their own project restrictions.

Provisioning refuses to replace global hooks owned by a different installation or an MCP entry for a different Deployment. This includes the retained 1.4 installation: keeping its local capture working takes precedence over removing dogfood overrides. The project-scoped mechanics described below remain for existing installations and their cleanup; the member CLI no longer creates them. A global MCP headers helper started outside a bound project resolves the explicitly named Deployment and sends no project header. Inside a bound project, its Deployment must still match.

**The member MCP entry is the Deployment's remote HTTP `/mcp` wherever the host can refresh a rotating credential** (#1237). A manifest declaring `memberMcpHeadersHelperKey` gets `url = <registry serverUrl>/mcp` plus `myco member mcp-headers --credential registry --server <serverUrl>`, with no token in the file. Codex uses `http_headers_helper` in `~/.codex/config.toml`; Claude Code uses `headersHelper` in `~/.claude.json`, its documented [user-scope MCP file](https://code.claude.com/docs/en/mcp#mcp-installation-scopes). The helper reads the registry each time and never rotates credentials. It verifies that the credential belongs to the configured Deployment. Project overrides retained for dogfooding still undergo the host-specific merge-conflict checks before any write. **Cursor keeps the stdio member bridge, an explicitly unresolved limitation:** its remote entries take static headers or OAuth and ignore a header helper. Static headers cannot follow a rotating member bearer, and the Deployment serves no MCP OAuth, so Cursor has no compatible refresh path (#1337).

**OpenCode and Pi member plugins install globally.** Their targets are `~/.config/opencode/plugins/myco.ts` and `~/.pi/agent/extensions/myco/index.ts`. Both hosts also load project plugins, so an existing project member plugin is removed after the global replacement is written. Existing dogfood project overrides use `memberHooksTarget` (`.opencode/plugins/myco.ts`, `.pi/extensions/myco/index.ts`), carrying the line `// myco:member-plugin`; their retained compatibility contract is:
- OpenCode's 1.4 plugin returns no hooks when any `.opencode/plugins/myco.ts` from `ctx.directory` up to `ctx.worktree` carries that line.
- Pi's member extension, as the last statement of its factory and only when its binary resolves as runnable, sets `Symbol.for("myco.member-extension")`, and the 1.4 factory returns when it is set.
- Provisioning refuses before any write while the installed global Myco plugin lacks `// myco:defers-to-member-plugin` (`MemberPluginConflictError`); a missing global plugin, or one Myco does not own, is no conflict. It also refuses, and leaves the file as it is, when the project's plugin path already holds a file Myco does not own. Both checks run in the one private writer (`writeMemberPlugin`) before its single write.
- The member plugins follow each host's callback contract. Pi calls `handler(event, ctx)`: the transcript is `ctx.sessionManager.getSessionFile()`, the prompt is `event.prompt`, and tools run as `execute(toolCallId, params)`, answering `{ content }` and throwing on failure. OpenCode's `chat.message` carries only the user message, so the assistant's text is taken from `experimental.text.complete`.
- `member leave` removes the member plugin, with or without `--purge`, only while it carries the member line, so the host falls back to its global plugin.
- **OpenCode's Myco tools use the global MCP registration.** `member provision opencode` writes `~/.config/opencode/opencode.json` `mcp.myco` as the stdio bridge `<member-home binary> mcp --credential registry`, the same shape Cursor keeps: OpenCode 1.18.21 has no header-helper field, static headers cannot follow a rotating member token, and the Deployment serves no MCP OAuth, so direct HTTP stays out of reach for this host (#1337 tracks the same limit for Cursor).
- OpenCode merges a project's `myco` server into the user-global one of the same name rather than replacing it: the project's `command` wins, while the global entry's `environment`, `enabled`, `url` and `headers` survive into it (`opencode debug config`, 1.18.21). `memberMcpGlobalMerge` marks the hosts that do this — Codex and OpenCode — and provisioning refuses before any write when the surviving keys would point the member's server elsewhere, give it another credential, or switch it off.
- `member leave` removes the member's MCP entry as well, with or without `--purge`, and only the entry that carries the member credential, so a 1.4 project install's server at the same name is left to the install that owns it.

### 3.5 Cutover

The transition is a **one-time, one-way import followed by disabling 1.4**: install 2.0 and join the Deployment, import the data, then disable or uninstall 1.4. There is no dual-running period, no id-parity reconciler and no community migration path; 1.4 has one user.

**The import has two sources, and every row reaches the Deployment through a route live capture or the tools already write through.**

- *The 1.4 vault* (`myco import --legacy <1.4 home | grove | myco.db>`, `member/legacy-import.ts`), for what no transcript on disk still holds. Every project in the vault goes to the Deployment Project of the same id, which the first write creates. Sessions, their prompts and responses, plans and the session's 1.4 title and summary go through `/events` on the `import` channel under a fixed producer, with event ids derived from the vault row, so a second run sends byte-identical envelopes. Spores go through `/spores/save` with their 1.4 id, status and time, and their supersede/consolidate history through `/spores/resolve` with the 1.4 event id; both inserts leave a held id as it is. A session 1.4 deleted is not imported, from the vault or from disk.
- *Agent transcripts* (`myco import`, `member/import.ts`), for every session after 1.4 stopped and every session with no vault row. A transcript is placed under the checkout its recorded directory sits in, the main checkout of a worktree that still exists, an explicit `--map`, or the checkout whose remote the transcript records; transcripts live capture drops (Codex sub-agent threads and `exec` runs) are left out the same way.

**One session id space, one content source.** A vault row takes the id its harness's transcript layout names for the same session (`legacyIdentity`, the matchers enumeration uses, any harness's layout for a recorded path). A row 1.4 minted an id for with no path is tied to the one transcript the same harness wrote in the same root while it ran (`aliasByTranscriptTime`), or keeps its id and is reported. A vault session's transcript, where one is on disk, ships under the vault row's own Project whatever directory it records; the vault's prompts and responses are sent only where no transcript reaches the Deployment. That choice is made once per session, before anything is sent, and recorded in this machine's import ledger (`member/legacy-ledger.ts`), which every later transcript import reads to leave those sessions out. A session the Deployment already holds keeps the facts and the end live capture recorded: it gets no start and no lifecycle end. The vault's title and summary ride on an import-channel `session.end` that names no instant, which the Deployment stores as the session's titling attempt and nothing else, never over a title an administrator set (`titled_by`). Any member on the same machine can name the import channel, so the channel is not an authority over titles; it is the owner's machine the import runs on.

**What is left out, and who records what.** What a person deleted in 1.4 (`session_tombstones.source = 'api_delete'`) is read from the vault on every run and left out of the vault import and of the transcript import after it, under its stored id and every harness id it resolves to; a duplicate row's deletion removes that row only. A deletion no layout resolves to a session is reported for the person to delete from the dashboard if it reappears. A deleted session the Deployment already holds (the transcript import a join runs can bring it before any vault is named) is found through the same session probe, reported for the owner to delete from the dashboard, and fails the import until it is gone; only what the Deployment does not hold is counted as left out. 1.4's own tombstones (a sweep, an invalid capture, a phantom) only keep a row out of the vault import. Rows another machine captured are left for that machine to import. No member route writes a tombstone: deleting a session stays the owner's. The Deployment records which sessions took their prompts from a vault (an import-channel prompt from the `legacy-import` producer), and `/import/plan` refuses a transcript for any of them from any machine (`vault_sourced`); this machine's import ledger only resumes a run. Every refusal the Deployment makes is reported, the session it refused is never recorded as done, and the import exits non-zero. Spore history keeps its 1.4 time on the member route's `channel: 'import'` (as `/spores/save` keeps a spore's `createdAt`), and a history event already recorded moves nothing when replayed, so a rerun never undoes a later status change. The import paces itself at 200 requests a minute, two thirds of the credential's rate budget, leaving the rest to live capture; it waits out rate limits and an unreachable Deployment for up to 30 minutes, and a step that waits that long stops the import, which reports every session, spore and history event it did not attempt; it retries another server error three times, and fails a step at once on a status no retry changes. A session whose transcript is still being written is neither decided nor sent, and is reported; a run after the transcript settles brings it.

**`myco cutover` does the whole move on one machine** (`cli/cutover.ts`). A read-only preflight builds the whole plan, and it is the only place the run refuses before a change; a dry run prints that plan and stops, and a test holds the dry run's plan equal to the real run's actions. It refuses when another installation holds anything the run would take: the `symbiont-config` claim in any home's claims folder, the machine pin (`~/.myco/runtime.home` must name the home the cutover runs under), a Myco hook, plugin or MCP entry at any place 1.4.8 registered one, or the MCP entry a 2.0 agent would get, judged against the Deployment's own URL. The places 1.4.8 registered are a checked-in list (`symbionts/legacy-registrations.ts`: global and per-folder hook, plugin and MCP targets and skills folders) that a test derives again from the 1.4.8 manifests, pinned to the `myco/v1.4.8` tag by git blob id, plus Claude Code's `projects[<folder>].mcpServers` in `~/.claude.json`. A plugin that declares a credential source is the member's; one naming another home refuses. A registration is replaceable only when it has no member credential, runs a binary under a 1.4 home being cut over (or a bare `myco`), and names no other `MYCO_HOME`. It also refuses a `myco daemon` unit it cannot attribute to a home, a boot-scope 1.4 unit, and a vault whose every session was captured under another machine id, and warns when some were. Then it backs up every agent settings file it changes into one folder of the 2.0 home, `backups/cutover-<stamp>/`, never beside the file: each original's absolute path is mirrored there with its mode, and `manifest.json` lists every original with its copy and sha256, every file the cutover creates (the pin, registry entries) and every skill link it repoints or removes, with `restore.md` holding the commands that undo each; the launchd unit and the claim files are copied there too before they change; a copy of a file the run leaves unchanged is dropped (every atomic write keeps a replaced file's mode), connects the folders, provisions the agents 2.0 captures over their 1.4 registrations in place, removes every other 1.4 registration (agents 2.0 does not capture are reported as no longer captured), checks that none is left, and only then points every 1.4 home's `symbiont-config` claim at the 2.0 home (a 1.4 daemon that comes back defers) and pins the machine. It stops the 1.4 daemon units it found by reading every `co.goondocks.myco*` unit file (its `MYCO_HOME`, else its working directory), never by computing a label, and leaves other homes' units alone; it asks each 1.4 home's running daemon to exit only when the daemon answering on that home's recorded port reports the pid the home records. It copies each vault (verified by a digest of every row the import reads, and taken again whenever the vault changed) and imports. A refusal or failure in either import fails the run, and a failed copy imports nothing.

**A 2.0 member home never runs 1.4 behaviour** (`member/home-role.ts`): a home that holds a Deployment membership or a cutover record is a member home, and for it the 2.0 binary never spawns the 1.4 daemon or asks a supervisor to start it (`DaemonClient.ensureRunning`, `spawnDaemon`), the daemon exits 0 at start, the service self-install and the global symbiont detection are no-ops, and credential-less `myco tool` and `myco mcp` refuse, naming `--credential registry` and `myco member provision`. So a 1.4 hook or MCP entry the cutover misses is inert: nothing it can call restarts 1.4. `tests/meta/member-home-daemon-gate.test.ts` holds every such path to the predicate and keeps the places a `daemon` argv is built a closed list.

The 1.4 homes and vaults stay on disk as a read-only archive; the import opens a vault read-only and nothing deletes it.

### 3.6 Run outcomes and the runner

A **run** is one prompt to one harness, on a worker, with declared expected evidence. There is no phased executor, no orchestrator, no resume and no turn budget: retry is the next tick, and steps are added only after a measured failure on a specific model. Partial writes stand and the run is marked partial.

**Four run outcomes and one config leaf** (plan §2.5; the map by #1378):

| Outcome | Replaces | Checkout |
|---|---|---|
| Continuous extraction and curation — create, supersede, consolidate | `extract-only`, `vault-evolve`, `supersession-sweep`, `review-session` | no; an empty scratch dir with a Myco-owned instructions file |
| Brownfield seeding from code and git history | `vault-seed` | yes; saves the Project’s first spores and a run report |
| Session titles and summaries | `title-summary` | no |
| The repository map — a directory skeleton and golden-path files, grounded in file digests | `canopy-map`, `canopy-background-scan` | yes; writes the Project's one map through `myco_run_map` |
| `instructions.template` (a Settings leaf, not a run) | `cortex-instructions`, `cortex-prompt-builder` | — |

`embedding-reconcile` stays a shipped server job. `myco_agent` stays the read surface over `agent_runs`.

**Instructions are config, not generation.** Session start serves a static, member-editable `instructions.template` (≤4 KB, Markdown, validated). With instructions static, a prompt builder has nothing to build, and the generated project digest is dropped with its loss recorded in §1 of the plan.

**Instructions to a run** are the prompt body plus a Myco-owned instructions file in the scratch dir — ACP carries user prompts only. Structured final output is not relied upon: a run succeeds by making MCP writes the server verifies afterwards.

**The runner** is a minimal **ACP v1** client over stdio plus native headless drivers — `claude -p --output-format stream-json --verbose --mcp-config … --strict-mcp-config` for Claude Code, `codex exec --json` for Codex — with the ACP driver serving OpenCode, Cursor and Antigravity. The published ACP adapters are npx packages, so native drivers are what keep **Node off every member and worker host**. One internal run-event model covers all three drivers and a gate holds them to the same contract; its five stop reasons are the protocol's own, and ACP v2 moves where they are delivered without changing what they are.

**Three launch shapes, not two**, which is why they are a manifest field rather than a rule applied thrice: a subcommand on the harness's own binary (OpenCode, Cursor), no protocol at all so a native driver reads the harness's own stream (Claude Code, Codex), and a sidecar binary the vendor ships separately (Antigravity). **Tool isolation differs the same way and only two of the five are airtight**: a flag that makes the run's configuration the only source (Claude Code), a redirected configuration home (Codex, whose inline server overrides otherwise add to the host's own), and additive for the rest, which the manifest states rather than a driver claiming an exclusivity it cannot enforce. **No driver decides its own run's outcome**: a run succeeds by making the MCP writes the server verifies afterwards, so a harness reporting success without them leaves a partial run.

**Workers** run the same binary in worker mode, and the laptop server process includes a worker by default. **One worker serves a Deployment per machine** (`runner/instance.ts`): a worker holds an exclusive lock under the machine's default home for every address its Deployment answers at — the native server's worker holds its loopback and its origin — and a second worker for that Deployment, from any member home, waits for the lock rather than claiming beside the first. A worker reads its credential from the membership before each request, so a rotation the hooks perform reaches a worker that has been running for days. A worker offers the harnesses it has installed and logged in, claims the oldest run it can serve from a Deployment-wide queue, holds it on a lease it renews, and drives the harness the Deployment chose. Lease renewal cannot extend beyond the run deadline. Harness and checkout disposal share a bounded cleanup window capped by that deadline; cleanup that does not finish within the window marks the attempt lost and stops renewal. **The Deployment decides every cadence and says it on each answer** — how long to wait before asking again, and how often to renew — so a worker carries none of its own and a lease changed on the server changes what every attached worker does. The claim is `POST /worker/claim`, a route scoped to the Deployment rather than to a Project — a worker names no Project, and the Project travels back on the run it is given. Only an administrator reaches it, decided at the pipeline: a claim answers with a minted run credential and a Deployment credential opened for the harness, and both are the Deployment's authority rather than a member's.

**Model lists.** A worker lists the models each harness it offers can run, the way the harness's manifest declares (`runner.worker.models`): a command printing one id per line (OpenCode's `opencode models`), or an exchange of JSON lines on the harness's own input and output, followed page by page where the manifest names a cursor (Claude Code's initialize request, Codex's app-server `model/list`), all read by one path (`runner/models.ts`) with no harness named in code. A listing is started through its driver's `launch`, the builder its runs start through, on the machine's own login: the same run home or `CODEX_HOME`, run agent and omitted variables, in a directory of its own that goes with it, so the machine's own configuration home is never written. On POSIX, every harness a worker starts, for a run or a listing, leads a process group of its own and is stopped as one (`runner/process-group.ts`: SIGTERM, then SIGKILL after a grace, then its close). On Windows only the harness leader is killed; descendant termination is not guaranteed. A worker lists once on attaching and again six hours after its last listing, in the background so no claim waits on it, and sends each harness's catalog on its own to `POST /worker/models` only where the Deployment advertises `model-catalog-v1`; a Deployment without it is sent nothing and the worker lists nothing. A catalog keeps up to 1,000 models within 192 KiB, each with its label and, where the harness says, its provider, whether it is the harness's default, what an alias resolves to, its successor and its efforts, and says it was made with the machine's own login; a model the harness's settings would refuse is left out. It is kept per machine and harness, the newest report replacing the last whichever of the machine's credentials sent it, and counts for twelve hours (two listings) from when the Deployment received it. Settings, to an admin only, offers each tier's model from the counting catalogs, filtered by provider where they span more than one, keeps a stored model no catalog lists and says it is not listed, names a listed successor, says whose login the list was made with where runs sign in with the server's login, and falls back to a typed model where no worker has listed the harness. A manifest's `runner.profile.presets` (OpenCode's newest Claude models through OpenRouter) are offered only where a catalog lists every model of the preset, and applying one writes each tier's leaf through the ordinary settings write. A claim records what the claiming machine's counting catalog lists the requested model as resolving to (`resolvesTo` on the requested profile; Claude Code lists its aliases' resolutions, OpenCode lists none). The run's model matches the request on the same id, the same id under the provider the run reported, that resolution, or a manifest-declared family alias (`profileModelMatches`); a model the manifest says its provider resolves at each request (`providerAliasPattern`, OpenRouter's `~` models) reported as another with no resolution listed is recorded unconfirmed (`model_unconfirmed`), never mismatched (`profileModelVerdict`).

**Run-directory cleanup.** `runner/run-directory.ts` owns each private attempt and model-listing home before credentials are written. Its version 2 manifest binds the persisted machine ID, worker PID, process nonce and harness owners. Whole-allocation and direct-child deletion share one disposal guard: no repository or other child is removed while a recorded harness owner remains. Hostname changes do not change ownership. Startup recovers manifested allocations only when the worker and all recorded harness owners are proven absent; uncertain probes, unfinished launches and foreign machine IDs retain the allocation. Discards blocked by a harness owner queue the whole allocation and are retried by the running worker before later claims and during final cleanup. Each retry visits every waiting allocation before surfacing filesystem or ownership failures together. Once the owners are absent, known credential files are deleted before other contents; a locked regular credential file is truncated to empty if unlink fails, and symlink or hard-linked login targets are never rewritten. Cleanup failures retain ownership metadata for another attempt. Once on each worker startup, an age-gated sweep examines unmanifested homes older than 24 hours directly under its run root: it scrubs only known credential-bearing configuration files, removes empty configuration/home directories, and preserves unknown files, malformed manifests and linked directories. The same age-gated retirement admits a structurally valid version 1 hostname-only manifest only after its worker and every recorded harness owner are proven absent; hostname differences are accepted inside this local run-root migration boundary because that format carries no stable machine identity. It scrubs known credential files and preserves unknown contents. A version 1 record with an explicit machine ID follows stable ownership checks instead, so a foreign machine is never retired by this fallback. New-format records require a machine ID. This repeats on later worker startups so homes too young for one sweep remain eligible later.

**Source-reading workers** advertise the capabilities they carry on the claim: `repository-checkout` for a checkout, and `repository-digests` for the digest listing a map run reads (`capabilitiesRequiredBy`, `@goondocks/myco-shared/repository`). A repository task goes only to a worker that reports everything it needs, and one that no worker heard from lately can take is held by the capability it waits for, which the dashboard shows as why it waits. A seeding or map claim carries only the repository URL, branch and history depth of 200. The worker opens the read credential and pins the commit through `POST /worker/repository`, under its administrator credential and current lease; the model's run credential cannot use this route or the legacy repository route. One checkout helper serves worker and retained container paths, with HTTPS-only Git, isolated Git configuration, disabled hooks and credential helpers, a 120-second preparation bound, a 256 MiB committed-file limit, and explicit rejection of LFS and submodules. Source lives at `repo/` in a unique scratch directory per attempt — for a map run beside `repo.sha256`, the streamed SHA-256 digest of every committed regular file whose path has no line break — and is removed when the attempt ends. A map run's input is pinned in the same step as its commit: the hash of the commit under the Deployment's exclusion patterns, and the map revision it succeeds (`pinMapSourceAtCommit`, `core/canopy.ts`). Codex source runs use a permission profile of their own that reads the run's directory and writes nothing, and, on macOS, reads the developer directory the system's `git` runs from once it passes `activeDeveloperDir`'s checks (root-owned, holding `usr/bin/git`, neither `/` nor above the home or the run's directory); Claude source runs use manual permissions with explicit file/history read allowances and no permission prompts.

The claim takes a row and binds its credential in one statement, so a run never looks healthy while its credential resolves nothing, and it rewrites the run's start so the task's budget bounds the run rather than its wait. **Lease expiry returns the run to the queue** with its credential retired and its place in line kept — a different question from a run outrunning its own budget, which is failed rather than requeued. The two claim paths stay disjoint by construction: a worker takes only a queued row that names no credential, and the two tasks the seam still serves never enter its queue.

Worker detection probes local binaries asynchronously and caches results for 30 seconds, invalidating the cache on claim or run failure. Detection reads local files and local processes, never the network — the published agent registry carries no credential field, so a probe is always of the tool itself. A Deployment declares a preferred harness with a fallback order (`worker.harness`, `worker.harness_fallback`), overridable per task through `agent.tasks.<task>.harness`; a cloud worker logs in once and its harness OAuth token or API key is held in the Deployment's encrypted secret store (class 3, §3.3.1) and injected per run. A laptop whose harness is already logged in needs none: the Deployment holds no key for it and injects nothing.

**A run's credential is a third principal kind** (#1145). A run token is not a member token. The pipeline admits the harness member's credential to two kinds of route only — a route that serves the run principal (`/mcp`, `route.run`) and the retained runtime channel (`legacyRunRoute` on `/runs/*`), whose shared pipeline admission binds the credential to exactly one dispatch, its Project, the body’s run id, its task capability and an unexpired attempt. Only claim and update admit a pending dispatch, and claim admits a queued launch still naming its credential; every task operation requires a live running row. Ordinary member credentials have no authority on this channel. A terminal update retry acknowledges the existing ending without writing; a credential retired by its own run release can read this acknowledgement until its original expiry, while every other operation remains refused — and refuses it everywhere else (`run_scope`), the refresh route included, so a run credential is never refreshable. On `/mcp` the one live run the credential dispatched is resolved from the credential alone (`heldRunOfCredential`: exactly one `running`, non-stale row names it, else `no_run`), the header must name the run's Project (`project_mismatch`), and the run's surface is its task's **declared** tools (`TASK_TOOLS`, `core/task-catalogue.ts`, held equal to the task files by a gate) mapped onto `(tool, op)` pairs (`mcp/run-surface.ts`) and enforced at the one chokepoint (`mcp/server.ts callTool`) with the same byte-identical refusal a grant gets; `tools/list` is narrowed to it, and a dry run keeps its reads and loses every write. Writes carry the run's agent as `agent_id` and the run id in the `author` column beside the dispatch-named session. A run's surface is two sets (#1146). Where its work is a member's work — every write of vault content, and search — it calls the catalogued tools, so one operation keeps one implementation and one attribution path. Where the operation is the run's own — an inventory of previews under a full-read budget, bodies cut to the task's window, full-fidelity session material, its state under a compare-and-set, its prompt cursor, its own session's titling material and title, and the map a map run keeps — it calls five run-only tools (`mcp/run-definitions.ts`) that are not in `SERVED_TOOLS`, are listed to no member and no grant, and have no member-side counterpart. Every bound comes off one `ReadWindow` per task (`core/read-window.ts`), so no handler names a task. `myco_run` op `report` is served to every run outside the allowlist: a report is the run protocol rather than a task capability, and a task declaring no tools of its own still has to close. Ten `/runs/*` routes are deleted with the operations that replaced them; fifteen stay as the worker's and the seam's own channel, and two of those — `claim` and `report` — stay for a reason that is not "no MCP tool does this": the push-launch seam's container reaches them over HTTP and speaks no MCP, so both go with the seam in #1170. The handshake is the principal's too — a member, a run and a grant each read instructions true for their own surface, rather than one string that told a bound principal its writes need an argument they do not.

**Close evidence** stays server-side, with the report channel and single-flight: a run closes only when the server can see the rows it owed. Each outcome names its row (`RUN_CLOSE_RULES`, `core/run-postconditions.ts`): a titling run the title it wrote on its session, an extraction pass a prompt it marked read, a seeding run a spore whose `author` is the run, a map run the Project's map row whose `source_run_id` is the run — each keyed to THIS run by a write the run itself landed, never by a row that merely exists. A report alone is the model's word and closes nothing that owes a row; a skip report closes a pass that found nothing to do only where the server's own read agrees (`skipHolds`: no unread prompt, a seeded Project, a standing title), else the run fails on its artifact. A map run's pass with nothing to do closes under its own action, `canopy_map_unchanged`, and its artifact rule reads that the current map was already read from the input the run pinned. The prompt a run is driven under is the Deployment's (`INPUT_BUILDERS`, `core/task-inputs.ts`), built at the claim, in the vocabulary of the tools the run's surface serves; the standing rules travel beside it as the instructions file the worker writes into the scratch directory (`writeRunDir`, `packages/myco/src/runner/mcp-config.ts`, under `AGENTS.md` and `CLAUDE.md`). A worker-served task the Deployment builds no prompt for is refused at dispatch as `no_instruction`; an outcome whose worker half has not landed (`UNLANDED_TASKS`) is refused as `not_landed`. External agents write under the same discipline through a per-project grant, attributed to the grant by an author column and an agent row, and may cite a PR or commit instead of a session.

**The wake tick is the only scheduler for Deployment work** — a `DeploymentClock` alarm with a cron floor on **W**, an in-process loop on **C**, both feeding one idempotent tick (`core/tick.ts`) with per-task per-day ceilings. Triggers are session end, the clock, and an explicit ask. The member binary registers no timers; the machine-side needs that survive — upgrade check, symbiont detection, managed-files reconcile — are the on-demand verbs `myco update` and `myco doctor`.

**Evals** gate the prompts: recorded real sessions as fixtures, redacted by a gate before commit, with a hand-annotated gold set of 30–50 cases; deterministic graders per PR against replayed recordings; a weekly (and on any task-prompt or skill change) judged run on a curated subset, capped per run; results on the KPI page and the weekly job required on releases.

## 4. Owning-surface vocabulary

Every ledger row carries one or more of these. This is the closed set the gate accepts.

| Code | Surface | Owns |
|---|---|---|
| **M** | Member Installation | Binary, hooks, plugins, spool, member registry, capture, member credential, **worker mode** |
| **MS** | Member Service | **Retired** (§3.4). Reconciliation is the on-demand `myco update` / `myco doctor` verbs, owned by **M**. The code stays in the gate's closed set; no row carries it |
| **Core** | Shared server core | Vault, query core, serving, run queue and close evidence, notifications, access grants — target-independent |
| **W** | Cloudflare adapter | Target-specific mechanism on Cloudflare |
| **C** | Self-hosted adapter | Target-specific mechanism on the self-hosted binary |
| **UI** | Server dashboard | Human surface served by the Deployment |
| **MCP** | Server MCP surface | Normal member MCP and external read-only MCP |
| **—** | none | DROP rows only |

`Core` alone means the mechanism is identical on both targets. `Core + W/C` means the need is shared but the mechanism differs per target and **both must be named** before the row is implementable.

## 5. Actor × deployment target × lifecycle matrix

Actors follow [`actors-and-boundaries.md`](actors-and-boundaries.md): the **Myco agent** (internal harness), **Symbionts** (coding agents), and **Users** (humans). 2.0 adds **Operator** (Deployment infrastructure lifecycle) and **External Agent** (read-only MCP, non-member).

| Lifecycle stage | User | Symbiont | Myco agent | Operator | External Agent |
|---|---|---|---|---|---|
| **Install** | Plugin alone → skills + MCP tools; the installer adds binary + hooks + capture + worker (**M**) | — | — | — | — |

## 7. The feature-preservation ledger

Every row: an exact registry token, a disposition, an owning surface, and the child that carries it.

**A row's disposition describes the code as it stands, not the code as it is planned** (plan §6). The gates in §9 and the four server gates that read this document hold the ledger against the tree, so a token that still exists carries the disposition it has today and names its planned fate in the reason column; the disposition changes in the PR that changes the code. A surface that does not exist yet is described in the **Planned additions** block under its subsection rather than given a row, for the same reason. `Blk` marks release-blocking (must close before `myco/v2.0.0`); `—` marks non-blocking follow-up.

Dispositions: **KEEP** — exists in 2.0 in recognisable form. **REPLACE** — the need survives, the mechanism changes; the replacement is named. **DROP** — the need itself disappears; a reason is required, and "no local daemon" is a reason only when the capability existed *to manage* the daemon.

### 7.4 Agent tasks — `packages/myco/src/agent/definitions/tasks/`

2.0 keeps four run outcomes and one config leaf (§3.6). The phased executor, turn budgets and per-task model routing do not survive: a task is one prompt with declared expected evidence, run on an attached worker. The `agent_runs` audit trail stays.

**A run's outcome is the Deployment's, not its runtime's.** Every retained task declares what one of its runs must have left behind — a report action, the row it owed, or both (`RUN_CLOSE_RULES`, `core/run-postconditions.ts`; held equal to this catalogue by `tests/myco-server/task-catalogue.test.ts`, which also holds the four outcomes, their close rules and their input builders (`INPUT_BUILDERS`, `core/task-inputs.ts`) to one another: no outcome without a rule and a prompt, no rule or prompt without an outcome). A worker-served task the Deployment builds no prompt for is refused at dispatch (`no_instruction`) rather than queued. Both front doors a run ends through judge the same rule: a container reporting over `POST /runs/update`, and a worker reporting for the run it leases over `POST /worker/end`. A `completed` report whose evidence is absent is recorded `failed` naming what was owed; the report is still accepted, so the lease ends and the run credential is retired either way.

**Auditable runs** (#1592). A run's record holds three accounts of what it did, and no transcript. What the Deployment observed is its own: every call the run made back with its operation, time, duration and failure, and every write that landed (`agent_run_events`). What the agent says it did is its report's **audit**: `myco_run` op `report` (and the container's `POST /runs/report`) carries `audit`, an object of `steps`, `examined`, `commands`, `failures` (each `{what, recovery}`) and `reasoning`, judged by its shape alone through the one door every report lands by (`recordReport`, `core/run-audit.ts`). It is refused only where it says nothing a reader can check — not an object, or no step or no reasoning — and is answered then as a failure that says so, the report recorded without it; everything else is repaired and the repairs are answered: an undeclared field or an empty entry is dropped, a long string is cut, a list past its bound is cut with the entries cut counted in `omitted`, and a failure given as text reads as one with no recovery. Each of the four outcomes' close rules is `audited`, and a run owes the audit only where a worker's claim recorded its attempt (`agent_run_attempts`), so a run claimed before attempts were recorded, or run by a container, closes as it did; a run that owes one closes `completed` only when a closing report carries it, and otherwise `failed` with `the run ended without its audit` under the reader code `report_without_audit`, its writes kept. Needs you names, per Project, the runs that ended so in the last week against the runs that owed an audit (`runs_without_audit`). Every outcome's prompt asks for the audit and to report again when the report answers with an error. **No command text is stored as written**: one allow-list rule (`commandShape`, `@goondocks/myco-shared/command-shape`) shapes every command-shaped string — a step's target on the worker and again on the Deployment, and an audit's commands — keeping only words of a provably safe shape: its first line (broken at `\r`, `\n`, U+2028, U+2029, U+0085, VT and FF), ending in `…` where a later line holds anything, without leading `NAME=value` assignments (after `env` and `export` too), with the line's first program kept as a safe name or a path and a later program (after an operator, or in a shell's `-c` script) only as one `KNOWN_PROGRAMS` lists, a subcommand only as the first positional word, before `--`, that the program's entry in `SUBCOMMANDS` lists, flag names, operators, and an argument only in a declared path-taking role and where it is a path (`.` or `..`, or a `/` or an extension `FILE_EXTENSIONS` lists, no `@ : = ? &`, not key-like judged over the whole word) and never after a flag whose name says it carries a secret; separate flag values are omitted unless the command declares that flag as path-taking; every other word, a group word (`!`, `(`, `{`) anywhere but where a program stands, and everything after a redirection up to the next command, reads `…`, and a URL reads as its scheme and host, taken after the last `@`, or its scheme alone where the host is key-like. An audit keeps a file examined only as a path, anything else reading `…`. A step's target is shaped by its kind: a search keeps only its path (the manifests read no pattern, query or glob, and a target with a pattern character reads as none), a fetch only a URL's scheme and host, and a Myco call its operation, which the Deployment keeps only where it is one of its own tools' operations (`MYCO_TOOL_OPS`); only a call to Myco's own MCP server reads as a Myco call. An agent-protocol call's free-text title is never read, and the call is named by its protocol kind. A failed call is noted on the run by its tool's identifier and a coded outcome alone (`refused`, `timed out`, `exit code N`, `failed`), never by anything the call said or returned. Masking known access-key shapes is a second layer after it. What the worker observed is the attempt's **step log**: each driver turns its harness's stream into calls carrying the harness's call id, input and exit status, and records it cannot read as `unrecognized` by shape; the harness's manifest says how a call reads as a step (`runner.worker.steps`: by tool name, prefix or the harness's own category, with the input fields its target is read from) and what a step names its call by (`runner.worker.stepTool`: the tool's name, or for an agent-protocol harness, whose call titles are free text, the call's own kind), and one implementation for every harness keeps each step's kind, identifier-only tool name, shaped target, outcome, exit status, times and call id (`runner/steps.ts`), never file contents or command output; a path inside the run's checkout, as given or as the filesystem resolves it, is written relative to the checkout before it is shaped (`<checkout>/packages/a.ts` reads `packages/a.ts`, and `git -C <checkout>` reads `git -C .`), since the checkout's random directory name would otherwise keep only as `…`, and a path outside it is shaped as before; the Deployment refuses a page whose tool or call id is not an identifier. A claim records its attempt in the batch that claims the run. Before the run's scratch directory is removed the worker writes the attempt's log to its outbox (`runner/step-outbox.ts`, under `<MYCO_HOME>/worker/steps/`) as the exact page bodies, at most 100 steps a page and 2,000 an attempt, and sends the pages over `POST /worker/steps` after `POST /worker/end` releases the attempt lease; a worker stopped before it delivered them sends the same bytes when it starts again, and the Deployment stores each page in one statement and keeps one row per attempt and step (`agent_run_steps`) however often a page arrives. A page the Deployment answers with a refusal ends its log and the next log is sent; a page it does not answer (a transport failure, a 5xx or a 429) waits. Every pass of the worker sweeps the whole outbox, every Deployment's directory whether or not it still takes step logs: a log older than seven days is removed, and past 64 MiB the oldest logs are removed first. A page is admitted by the attempt it names, from the worker credential that claimed it or another credential of its machine, never by a live lease, and writes only the attempt's steps and totals, so a log arriving after its run ended or another attempt took it changes no status or accounting. A worker sends a log only to a Deployment advertising `worker-steps-v1`; a worker that sends none closes its runs as before, and its attempts read as having no log. Run retention deletes a run's step log first, at most 10,000 rows a pass, and keeps the run with its turns, reports and attempts until its log is gone. The run's detail serves every report with its audit, the run's latest 50 attempts with what each log holds and how many attempts it has in all, and the first page of the latest attempt's steps; `GET /api/projects/{projectId}/runs/{runId}/steps` pages any attempt's log by its id. The run's panel on Myco's work reads the three together through one projection (`ui/src/features/work/activity.ts`), with no per-harness branch: what a harness's own tools did reads from its manifest's step rules (`words`, generated into `@goondocks/myco-shared/runner-step-words.generated`), and any other tool by its name in plain words. "What it did" lists each attempt's steps in order, a Myco call the worker also saw folded into its step: calls and steps share no id, so a step of kind `myco` pairs with a call of the same tool and operation inside the attempt whose claim the call followed, nearest first (inside the step's span, then nearest its end, since Myco records a call as it answers it) and within 30 s of the step on the two clocks, so a step with no call or a call with no step leaves every other pair as it was. An agent-protocol harness names a call to one of Myco's tools as its manifest declares (`runner.worker.mycoCalls`: a name form with `{tool}` compared whole with the call's name, or the server and tool its input names), read through one function (`runner/drivers/acp-myco.ts`) by the grant and the step log alike, so its Myco steps pair as Claude Code's and Codex's do; where a list holds steps and Myco's calls but no step names a call to Myco, it says so. Every page of calls and steps is read, and a list is shown 200 rows at a time against its true total. A step's manifest names the stream records that never carry a call (`runner.worker.notSteps`: Claude Code's thinking, rate-limit, slash-command, hook, status and compaction records; an agent protocol's plan, command, mode and user-message updates), which are not counted, so the unrecognized count is only of records that might have held a step. Each list says how much of the evidence it holds: complete, partial (steps not yet arrived, past the log's bound, not loaded, or records that might have held one unread), pending (an attempt whose log has not arrived) or unavailable (no attempt recorded, or its log could not be loaded); no part of the panel says a run read nothing where its evidence is missing. "What it read" names the sessions Myco served it and the files its read steps name; a search, a directory listing (Claude Code's `LS` reads as a search) or a command is activity, never a read. A failed step is retried only where a later step of the same kind has the same shaped target, keeping every word; a later success of the same Myco operation is said as one and is not counted as a retry, since what each call carried is not recorded. A reclaimed run shows each attempt apart, with why it gave way: a claimed run returns to the queue only when its worker stops checking in. The agent's account sits beside the list in plain words, checked by fixed rules against the attempt it closed, and not at all where Myco can't place it in an attempt: a kind of step the worker saw that the account leaves out (commands run, files read, steps that failed or were not allowed) and a command or file the account lists that no step names are flagged as facts. Only what is provably different is flagged: both sides of a comparison pass through `commandShape`, a claimed command matches where its words appear in a step's command in order (so `npm test` matches `npm test -- tests/a.test.ts`, and is found inside a list or pipeline), a claimed area covers the files under it, and where a shaped form holds `…` (a word not kept, or a later line dropped), or the log is partial, the check says it can't compare rather than flag.

**Stored diagnostic detail.** The shared `diagnosticDetail` boundary omits arbitrary words, including text that imitates a canonical run error, and bounds the result. Codes come from trusted structured fields or classification, never from retained payload text. Arbitrary harness stderr, file excerpts, command output, provider bodies and exception messages read `…`. The worker's local diagnostic log uses this boundary; it retains the run, harness and coded error, with owner-only modes, size rotation and a fourteen-day age bound. Embedding source-failure and switch reasons use `embeddingDiagnostic`: a run diagnostic code, the HTTP status where supplied, and bounded masked detail. Workers AI classification reads bounded original words before projecting them, so input refusal and daily quota still drive the same pass-over and retry behavior. Agent prose omits fenced, indented, blockquoted and structured JSON output before single-line normalization; Secret label recognition compares compatibility-normalized name components while copying ordinary prose unchanged; quoted values are omitted across line breaks. Declared token quantities retain only decimal literals in display redaction. Command argument roles distinguish path-only modes, explicit patterns and clusters of declared boolean flags.

**Historical stored text.** Upgrading does not rewrite existing `embedding_source_failures.reason`, `embedding_switches.reason`, report/audit rows, step artifacts or local diagnostic logs. Rows that already contain verbatim provider bodies or other payloads therefore remain in storage and may remain visible through existing read surfaces. Source-failure rows are replaced by a later failure for the same source/model, removed after a successful vector write, or removed by the existing reconciliation lifecycle. Switch reasons clear when progress or resume clears them; deleting a switch removes its row. Local diagnostic files expire through the existing write-time age pruning and rotation, so an inactive worker's old files are not automatically purged. Backups and exported artifacts remain unchanged. No schema step or retrospective sanitization is performed by this upgrade; the privacy guarantee applies to new writes.


**Worker accounting.** Native workers report cumulative usage with their claimed attempt id on `POST /worker/end`. The Deployment validates counts and dollar values, resolves cost through `core/cost`, and writes accounting and final status atomically under the current worker lease and dispatch identity. Duplicate or stale attempts cannot replace the recorded values. Unknown counts and cost remain null. Claude's query-wide `modelUsage` includes cache reads and writes; its `total_cost_usd` is a harness estimate, stored as `estimated` with no actual charge. Codex reports inclusive input/output counts and cached input, with cost `unavailable` when no price is reported. Dashboard and MCP read the same persisted record. Older workers and claims without an attempt id can still complete without reporting accounting. Recording cost does not enforce a spending cap.

### 7.5 Scheduled jobs — `packages/myco/src/constants/power-jobs.ts`

**The server-side wake tick is the only scheduler, and it schedules Deployment work only** (plan §2.5). The member binary registers no timers: the machine-side needs that survive 1.4's JobRunner — upgrade check, symbiont detection, managed-files reconcile — become the on-demand verbs `myco update` and `myco doctor`, run by the setup skill and the installer. PowerManager, its four power states and its ~24 machine-side jobs retire with the daemon (plan §5).

One idempotent tick (`core/tick.ts`) runs the due jobs, applies per-task per-day ceilings and drains the run queue; `POST /api/wake` runs the same tick on an ask. **One registry declares everything scheduled** — `core/jobs.ts` carries both tables, the tick's own jobs (`SERVER_JOBS`, implemented in `jobs-run.ts`) and the tasks the clock dispatches (`TASK_SCHEDULE`, decided in `scheduled-tasks.ts`) — and `tests/myco-server/one-scheduler.test.ts` holds the Deployment to it: a process timer appears only in `platform/bun/wake-loop.ts`, a hosted alarm only in `platform/cloudflare/deployment-clock.ts`, the cron handler only in `entry/cloudflare.ts`, and the tick is the only caller of the clock. On the member side `tests/meta/member-no-timer.test.ts` walks the import closure of the 2.0 entry points (`src/hooks/**`, `src/member/**`, `src/runner/**`): it reaches no daemon module, names no PowerManager, and holds only timers bounded by something already running — one HTTP request's budget, a hook's own re-read, and the lease heartbeat of a run a worker already claimed.

**A named precondition is asked with the store it decides over.** `PRE_CONDITIONS` and `ACCELERATORS` (`core/scheduled-tasks.ts`) take the relational store beside the Project id, so a condition about a Project's data can read that data — a hook that could not would be a condition about nothing, which is why both tables shipped empty. The store, not the whole Deployment: deciding whether to run is a read. The first one registered is `has-unprocessed-prompts`, one page of one row over `listUnprocessedPrompts` (`read/prompts.ts`) counting no prompt of a session still being written. The hourly `extract-curate` schedule names it (§7.4).

**Every registry read goes through one chokepoint**, `declared` (`core/declared.ts`, a leaf so each registry module can share it), which reads own properties only. Plain indexing answers `constructor`, `toString` and `valueOf` with callables from `Object.prototype`, and the names reaching these tables come from outside the code: a precondition or accelerator from a Settings leaf, and a task name from a dispatch request body. Unguarded, a settings string would have admitted a task no condition passed, or shortened an interval twelvefold through an "accelerator" that is the `Object` constructor; and the **primary unknown-task guard** (`admissionForTask`, with `taskTools` and `runTimeoutForTask` beside it) would have answered `[class Object]` for a task named `constructor`, so `prepareDispatch` queued a worker-served run instead of refusing `unknown_task`. All four read through the chokepoint now, pinned over the six inherited names. A schedule naming a precondition or accelerator absent from its table is refused by a gate rather than skipped in silence every wake.

Automatic schedules count their own runs over a trailing 24-hour window. Ad-hoc owner requests bypass this ceiling and do not consume automatic slots or reset the automatic interval. Both paths retain the shared concurrency and execution limits; a request waiting for execution capacity queues normally. The dispatch records its actor on direct and queued runs, and replacements retain that attribution. Older runs with no usable actor count conservatively against the automatic budget, including their replacements.

Extraction allows 12 automatic runs per trailing day. Three slots are reserved for live sessions that ended within the trailing 24 hours, have unread prompts, and have fully parsed transcript material. History-only work stops after nine automatic runs. The reservation uses the same primary-session selector as extraction: completed live capture takes priority over imports, then the newest eligible session wins. At least one quarter of each multi-prompt page remains available to other sessions, so a recent-session run can also advance history. `agent.tasks` schedule overrides can change `reservedRunsPerDay.count`; zero disables the reservation. Ad-hoc extraction remains available at either automatic threshold.

A refused automatic run is not queued. The next wake checks the trailing window again. The clock records `max_runs_per_day` or `reserved_runs_per_day` once per refusal episode, keyed by project, task, filling instant and refusal reason. Skipped rows consume no slots. An episode spanning midnight retains its row; a replacement can move the filling instant and create another refusal row without increasing the count. A zero ceiling with no prior entry uses one stable refusal row. Tests cover these decisions in `tests/myco-server/scheduled-tasks.test.ts`, owner requests in `harness-dispatch.test.ts`, replacement accounting in `replaced-runs.test.ts`, and the scheduler on both deployment targets in the `scheduled-tasks` parity scenario.

**Waking is the only platform-specific part**, and on the Worker that instant is a **Durable Object alarm**, not a cron trigger:

- An alarm takes an absolute time at **millisecond** precision and is re-armed on each fire — the same shape as the `setTimeout` it replaces. A cron expression bottoms out at one minute and cannot express a computed interval.
- **No alarm set means nothing runs**, and it costs nothing. A cron trigger fires whether or not there is work.
- Cron triggers are capped **per account** (5 free, 250 paid), so making them the primary waker would ceiling how many Deployments an account can host. Alarms carry no such cap.

A **low-frequency cron trigger is still configured, as a recovery floor**. An alarm is state held inside the Durable Object: if it is never armed — a defect, or a Deployment that has never taken a request — nothing ever wakes and the failure is *silent*. Cron is externally guaranteed and is the only thing that recovers that. It is insurance, not the mechanism.

Alarms may fire more than once, so **the tick must be idempotent**: each evaluation re-probes its sources and recomputes rather than accumulating, and a gate fails by name if a tick ever carries state between invocations.

The port is `ServerEnv.wake` — "wake me soon", called by requested work — with `DeploymentClock` (a Durable Object alarm, `*/15` cron as the floor) arming the instant on W and the process wake loop in `platform/bun/wake-loop.ts` on C.

**Where the parse runs, and why it is not a Durable Object request.** Plan §2.2 states that parsers run "inside a Durable Object request on Cloudflare (30 s CPU)". Two facts measured against the tree and against Cloudflare's published limits (2026-09-08) put the mechanism elsewhere, and the decision — parsers server-side, per agent, on both front doors — is unchanged by it.

- **The CPU claim is unverified for the Free tier.** The Workers limits page gives one tier-split CPU table, 10 ms on Free and 5 min (default 30 s) on Paid; the Durable Objects page publishes a DO-specific row of 30 s that is *not* tier-split. The DO relaxations that are unambiguous are wall time, which was never the constraint.
- **The binding constraint is subrequests, and a Durable Object does not relax it.** Free allows **50 subrequests per invocation**, D1 and blob reads both count, and each event ingested through its own batch spends one.

Measured: an 8 MiB segment of a real Claude Code transcript parses in ~11 ms, which is one whole free-tier CPU budget — and that figure is `JSON.parse` alone, before deriving, hashing or writing. So the parse is a **tick job bounded by the database calls a pass may spend**, resumable over a byte cursor, landing derived events in one batch. On the Worker the tick's own timer already *is* a Durable Object alarm, so any CPU headroom that exists is inherited with no new class, binding or migration tag; on the binary the same job runs in-process. Nothing under `platform/` differs between the two, which is what §3.3 requires. A per-target parse entry was designed and dropped on these numbers.

**Transcript identity, and what the head digest does not cover.** A transcript is named by (machine, path, inode). A file truncated and rewritten in place keeps all three, so the server records a digest of its first bytes and refuses a segment that disagrees with the one held — terminally, rather than appending one file's bytes to another's record. Two limits are stated rather than implied: a rewrite leaving the first bytes intact passes, so this catches replacement and truncation rather than every edit; and it is **inert until the member sends the field**, which is C1's half (**#1155**). C1 must ship sending and re-minting together — sending alone would park a transcript on a refusal it cannot answer.

**Fidelity is a property of a format, not of a file.** Cursor's transcript carries no tool results, so no parse of one can produce them and a session captured from it is structurally incomplete. Each parser declares what its format supports, the transcript records it, and extraction excludes such sessions **by default at the read layer's own definition** rather than by an argument at each call site: `listSessions` defaults to full fidelity and `listSessionSummaries` opts out, so a reader that assembles material inherits the rule and a reader that shows history does not. The dashboard still shows them: a hidden session is an absence a person can see, while a spore extracted from a knowingly incomplete transcript reads exactly like a good one. Only one of those is discoverable after the fact.

Codex currently retains `no_tool_results` and its fallback tool hook. Its parser reads paired `function_call` and `custom_tool_call` items with string or content-array outputs. The redacted Codex 0.153.4 recording in `tests/fixtures/codex-0.153.4-redacted.jsonl` proves the custom-call pair. Local-shell, tool-search and web-search variants remain outside that recorded coverage; full fidelity is not claimed.

**A row already stored wins, and a backfill must not inherit that.** A derived event is named by the row it produces, so a refusal on that name means the row exists with *different* content — an older parser's, or a hook's. The parse keeps the stored version and moves on, emitting `transcript_row_conflict`: stopping a transcript over one row already recorded would cost every row after it. That is the right default for a live parse and the **wrong** one for the bounded import (**#1148**), which re-reads transcripts over rows something else already wrote. Import needs an explicit rule for which version wins; it must not adopt this one by inheritance.

**An unreadable line does not silence a transcript.** A line that is not JSON is skipped and counted, and only a run of them past a threshold stops the file — losing thousands of rows to one corrupt line is the larger data loss. A stopped transcript records the parser version that stopped it and is offered again once that moves, so a format break is answered by the same deploy that fixes it rather than leaving files permanently dark.

### 7.8 Config leaves — `packages/myco/src/config/schema.ts`

1.4 resolves settings across four tiers — `machine`, `grove`, `project`, `local` — through `SCOPE_REGISTRY` (`packages/myco/src/config/scope.ts`). **2.0 keeps two**: Member Settings on the machine, Deployment Settings on the server (§6.1, and the `config` and `/settings` rows above). Every leaf therefore needs somewhere to land, and a leaf nobody placed is a setting that silently changes meaning.

Classification is **per leaf, not per registry row**. Seven of the registry's 31 rows are block prefixes covering many leaves, and a block is exactly where a mixed disposition hides: `release_provenance` is repo-specific except for one interval, and `notifications` is retired in 2.0. Bulk-mapping either would have moved a setting to the wrong side of the seam without anyone seeing it.

**Tier** is what the leaf becomes:

- **Member** — stays on the machine. Capture, symbiont, spool, log and machine preferences never become server state (#915 scope).
- **Deployment** — one value for the whole server, managed by any member (§5 Admin row).
- **Project** — per-Project state on the Deployment rather than config. Capability admission and repo-specific settings live here: a Project is created on first use (`resolveProject`), so its settings cannot live in a file that must exist before the Project does.
- **—** — dropped; mechanism rather than setting.

**Coverage is measured against declared leaves.** `declaredLeafPaths()` walks the schema rather than a defaulted instance, including optional leaves. A retired Deployment value moves to `retired_deployment_settings` before its leaf leaves the contract; the active registry names only leaves with a consumer.

**Only admins write Deployment settings.** Any member reads them, with URL secrets redacted for non-admin readers. Credentials are sealed, masked and attributed to their writer. Worker harnesses read only their declared credential slots; embedding clients send credentials only to their provider's fixed endpoint. Custom embedding endpoints receive no stored Deployment credential. Normal intelligence runs use worker execution profiles; the retained container probe alone uses the three `agent.provider` preferences.

**Project capability gates are fail-closed.** The Deployment admits `cortex`, `canopy` and `vault_evolution` per Project. An absent capability row reads disabled, so a Project created by capture starts capture-only until an admin enables context, mapping or learning. Shipped skills require no capability gate.

Four blocks hold dynamic children the schema cannot enumerate — `agent.tasks`, `notifications.domains`, `symbionts` and `release_provenance.package_map`. They are classified whole, as their own rows below, and the completeness gate collapses any leaf beneath them onto the block prefix.

The leaf registry (`core/settings.ts`) and this table are held equal in both directions. Execution profile leaves replace the retired provider maps. A reset clears one configured leaf through the same writer and restores its built-in value.

**The settings contract.** Every live leaf has a typed rule (`DEPLOYMENT_LEAF_SPECS`) the writer applies before storage, and belongs to exactly one policy in `core/settings-policies.ts` whose `resolve` calls the consumer's own resolver. Only a policy's owners read the settings table: consumers read through `settingTexts`, which hands them only stored values that hold their rule, or through `storedSettings` where a refused value must not fall back to a default that deletes or stops more — run retention clamps to its bounds, backups keep running at the nearest interval, recovery copies and manual exports are all kept, and the map period clamps. A stored value the rule refuses is reported where it is read, with what applies meanwhile. One answer reads the settings table once; a policy that cannot resolve reports its leaves as `unknown`. `GET /api/settings` answers each leaf with `stored`, `effective`, `source`, `state` (`active`, `inactive`, `not-applicable`, `invalid`, `unknown`), `reason`, `appliesTo` and `revision`, from those policies. The embedding selection is resolved per target by `core/embedding/policy.ts` and written whole through `PUT /api/embedding`, as one compare-and-set; while search holds results, every change of the model identity is refused and offered as Switch embedding model instead (#1603): `POST /api/embedding/switch` with `confirm: true` records one switch per Deployment (`core/embedding/switch.ts`, table `embedding_switches`), the in-process embedding run writes every source under both models and retires neither, search keeps the current model, and the embedding leaves move in the batch that ends the switch once every source holds a vector under the new model; `POST /api/embedding/switch/estimate` answers the sources, tokens and published cost the confirmation shows before it can be agreed to; only Projects that are not archived are built and counted, an archived Project's runs only retire, and a source whose stored text cannot be read, or that a model refuses as input (HTTP 400, 413 or 422, or Workers AI naming the input), is recorded in `embedding_source_failures` and passed over by every embedding run with or without a switch, counts as done, and is named with its reason in the confirmation, the progress and on Health (`GET /api/embedding/passed-over`); spores are calibrated under the new model while it is built, and search moves only once every Project is calibrated; a busy, slow, unreachable or rate-limited provider, or one whose daily quota is spent, is asked again after a growing wait (until the quota renews, or as long as `Retry-After` asks, up to six hours), while one that turns the key down, refuses the request, or answers results too large for search pauses the switch with its reason; `POST /api/embedding/switch/{id}/resume` resumes it, or asks a held-off model at once, `DELETE /api/embedding/switch/{id}` cancels it and the existing reconcile retires the partial vectors, and `GET /api/embedding/switch` reports progress, the wait, a switch that has not moved for 30 minutes and the passed-over sources for Settings and Health, both of which read it again while it stands; a recovered copy of a Deployment holds its switch paused until an admin there resumes it; `GET /api/settings` carries the providers and models the target offers, each model's vector size, and why one cannot be chosen. `tests/myco-server/settings-contract.test.ts` holds every live leaf to a policy, a consumer a production entry reaches, and a behavior case on each target. Its `taskTiers` table answers every outcome in `TASK_TIERS` with the effective tier and `task` or `task-override` source. The Settings task tier editor updates only `reasoningLevel` inside the existing `agent.tasks` document through the same writer, preserving each task's schedule, harness and model pin.

**There is no document write, so there are no siblings to drop.** A change on the page is one `PUT /api/settings/{leaf}` carrying one `value`, applied by the single validated operation in `core/settings.ts`. The form holds no copy of the Deployment's settings to write back, which is what makes the classic silent-data-loss shape — one field edited, every sibling overwritten with whatever the form happened to hold — unreachable rather than merely avoided. Held by `tests/myco-server/settings-leaves-round-trip.test.ts` (each leaf written in turn over the route, every sibling read back intact, a refused value changing nothing) and by `tests/myco-server-ui/settings.test.tsx` (one edit, one request, one leaf, one key in the body).

**Retired settings preserve stored history.** Schema step 68 copies each obsolete Deployment row into `retired_deployment_settings`, checks the copied value and attribution against the active row, then removes that row. The shared writer refuses both PUT and reset requests for those removed leaves. Operators can inspect their original JSON, actor and timestamp through the archive query in §7.6; complete Deployment recovery copies carry the table. The Settings catalogue and Older settings omit them. Generated digest and generated-skill controls and the skill project capability are removed; their tables and routes remain for P10's separate schema retirement. The retained container probe takes its provider only from the current Anthropic credential slot and its model from the current Claude Code default-tier profile; it reads no `agent.provider.*` setting or task-level provider/model preference. Titling is admitted by capture capability and uses the worker execution profile. Static instructions, whole-project Canopy, semantic search and shipped skills remain.

Machine revision history retains the five most recently delivered revisions per machine. An ordered report outside that window withdraws a stale confirmation; an already confirmed revision can still name its retained cached values. The machine receives the current revision again. Confirmed cached values survive pruning independently of the sent snapshots. Revision support is recorded for the requesting machine, and a member without it is described as applying settings at its next session start without reporting application. Portable backups omit sent snapshots and machine report metadata.

**Project-tier `release_provenance.*` lives in `project_release_provenance`, one row per Project, written only through `core/release-provenance.ts`.** `setLeaf` still refuses these leaves: they are not Deployment settings, and the Project Settings page writes them as one revisioned `PUT /api/projects/{projectId}/release-provenance`, refusing a stale revision. The GitHub credential is sealed in its own slot and read only by the release check. A session's release state is classified from its latest captured commit — the end commit once captured; `unknown` while only the start commit is known or when tracked files differed from the end commit — and a released state changes only for a newer captured commit, keeping the state it replaced.

**Rollout order: the Deployment before its members.** Capture carries the session's commit as `headSha` on `session.start` and `session.end`, and `dirty` on `session.end`; an end whose member could not read `dirty` omits it, is recorded with `error = 'status_unreadable'`, and its session's release state is `unknown`. A Deployment older than schema v46 refuses those payloads as `unknown_field`, so a Deployment is upgraded before the members that capture into it.

**An import's session title needs a Deployment that stores it.** A 1.4 vault import carries each session's title and summary as `title` and `summary` on its `import`-channel `session.end`. A Deployment older than those fields refuses them as `unknown_field`, and the import stops before sending any session when the Deployment does not answer what it holds of the sessions it names (`/import/plan` `sessions`), which ships in the same release.

**What a record's shape may change is part of the member protocol.** A field outside its declared shape or bound is refused `invalid_field`, which a member treats as final for that record and drops; an unknown field or kind is `unknown_field`/`unknown_kind`, which a member holds for a newer Deployment. Widening an enum (a channel, a prompt origin, a plan status or source, a transcript role), adding a required field, or changing an exactly-one or at-most-one pair therefore changes what one side drops from the other, and ships as a member protocol bump, never inside one. `tests/member/protocol-pins.test.ts` pins those judgements from the worker's catalogue per protocol, so a change to any of them without a new protocol row fails there. The enum lists are one source (`@goondocks/myco-shared/member-protocol`): the worker's catalogue admits them and the member's emitted prompt origin, plan status and transcript role are typed from them, so a member cannot emit a value its own protocol's Deployment refuses.

Backup policies have separate consumers: daily/weekly counts retain manual relational export copies; `backup.recovery.keep_stagings` retains full recovery copies on hosted and native targets. `backup.dir` is operator configuration. Maintenance checks run through the `database-optimize` and `database-integrity-check` jobs.

## 8. Release blockers

`myco/v2.0.0` publishes only when every gate below is satisfied on live data. Each is the plan's own gate (plan §8), and each fails by observation rather than by claim.

1. **Fresh machine.** Plugin alone → a first tool answer; one installer command → first injection, a captured session **and a spore**, on Claude Code, Codex and Cursor.
2. **Sandbox.** A sandbox holding only a join code captures a session and its plan.
3. **External agent.** Copilot code review reads context over MCP with a grant and saves a spore whose author is the grant.
4. **Workers.** A worker on a laptop and a worker on a VM each complete the four run outcomes with close evidence, on at least two harnesses.
5. **Both front doors** pass the same ingest parity and eval suites.
6. **KPIs.** The page shows the six measures with n, from live data.
7. **After the sweep** (plan §5): `packages/myco/src/agent/` is gone, the capture surface is under 4,000 lines, no daemon, Compose, Containers, digest, per-file Canopy, Team-Host or skill-lifecycle code remains, and the ledger gate in §9 passes.

## 9. The gate

A ledger with no gate goes stale the first time someone adds a CLI command.

`tests/meta/feature-ledger-completeness.test.ts` scans the registries that define the surface and asserts that **every token appears in a §7 table with both a disposition and an owning surface**, failing by name when either is missing. The 1.4 registries are the CLI dispatch in `packages/myco/src/cli.ts`, the routes in `packages/myco/ui/src/App.tsx` (retired with that dashboard, its rows kept as the record), the `TOOL_*` constants in `packages/myco/src/tools/definitions.ts`, the task YAML filenames, the `POWER_JOB_NAMES` values, and the 1.4 config schema's declared leaves; 2.0's are the dashboard's route table (`packages/myco-server/ui/src/routes/table.tsx`), the retained tasks, the task schedule, the server's tick jobs, and the Deployment's admitted settings leaves, preserved retired settings metadata and a machine's settings leaves; the data classes are every `CREATE TABLE` under each package's `src/db/`.

Each registry owns a §7 section, and its tokens are looked up there alone. The check runs both ways: every KEEP or NEW row in a section a live registry owns must be a token one of its registries produces, so a kept capability whose code is deleted fails by name, and every section the ledger parses must be owned by a registry.

A 1.4 registry is retired by deleting the code that holds it: its §7 rows stay as the record of what became of each capability, and the registry is named in the gate's `RETIRED_REGISTRIES`. A registry whose source is gone and is not named there fails, so a move or an accidental deletion never passes for a retirement.

`tests/meta/no-1-4-reach.test.ts` walks the import closure of the 2.0 entry points, the CLI and every verb it dispatches included, and stops at the 1.4 tree. The boundary is closed: every file under `packages/myco/src` is reached, inside the 1.4 tree, or named with why nothing reaches it. A 1.4 path named in a `package.json` script, a Dockerfile, the Makefile or a CI workflow is named too, with its phase.

The surface half is the one that matters most: a row with a disposition but no surface is how a capability ends up owned by nobody. That is the defect this whole ledger exists to answer.

### Transcript continuation and deployment recovery

The transcript parse job persists pending calls, plan ordinals and the current turn's reply text with its cursor. Replies join assistant records through a turn boundary and retain the first assistant offset. A durable member Stop closes reply text whose latest source timestamp precedes that Stop; unresolved calls remain pending. Equal timestamps wait for a later boundary. Undated records use the parse timestamp and may wait for the next prompt or idle bound. Terminal batches fence the exact selected continuation as well as its cursor, size and latest receipt. At a declared complete file, a settled session end (35 seconds), or ten minutes without transcript bytes, remaining calls become failures and pending state clears. A later successful result upgrades the failed tool projection. At most 32 calls remain pending; excess calls become failures naming the pending-call limit.

Parser version 5 rereads at most four older persisted cursors per wake through the ordinary bounded parse job. Rewinds preserve flat header metadata and resume from the committed cursor. Live bytes are selected before imported history and repair rereads. Live and repair transcripts rotate by their last parse instant, with unserved transcripts first. Repair takes one bounded pass per wake and receives a quarter of the call and wall allowance while live work receives half. An older chunked checkpoint without a byte baseline takes a background pass only when its last receipt strictly precedes its last parse instant; an equal-time or unserved checkpoint gets a live pass to establish its byte baseline. A new segment promotes a repair transcript to live work; the selection and pending count share the same work predicate. Absent raw source, a missing retained prefix, or a gap in the already-read prefix records a named repair omission instead of replaying guessed offsets. Retention-pruned bytes and conflicting previously stored response bodies cannot be reconstructed; their stored rows remain. Repair does not reconstruct missing transcript uploads or repair records no registered parser can interpret.

Schema step 70 adds checkpoint storage and parse-selection indexes. A coordinator backup precedes deployment. A code-only Cloudflare rollback leaves this schema and advanced continuation cursors in D1: an older parser does not understand pending replies and calls. Rollback recovery requires the pre-deploy operator backup into a fresh compatible deployment, or a forward fix followed by the bounded reread while raw bytes remain. An older native binary refuses a newer schema. Preserving legacy flat metadata fields supports header readers; it does not make parser-state rollback safe.

### Recovery tenant identity

A replacement restore is the same Deployment tenant. Native and Cloudflare recovery into fresh resources retain the snapshot's `schema_meta.deployment_id`, membership, ownership and live authority. Separate URLs or resource directories for the replacement do not establish a new tenant. Replacement requires `--source-retired`, the operator’s acknowledgement that the old serving instance is retired. An archive cannot prove remote retirement. Fork is required when the source remains in service.

`myco server restore --target local|cloudflare ... --fork` creates a new tenant. The shared recovery preparation rotates `deployment_id`, revokes copied member credentials, invitations, account-link authorities, external agent grants and step-up authorities, and ends copied active runs. It keeps historical rows, raw provenance and ownership. Independently held wrapping material still opens the carried sealed provider keys; the sign-in secret is fresh. The owner signs in again and reconnects machines to obtain fresh authority. The source artifact is read-only. Cloudflare's preparation journal pins the tenant mode and the prepared identity through retries.

Dashboard sessions carry the serving Deployment id as a signed audience. Missing or mismatched audiences are refused, including when two Deployments are configured with the same signing secret and linked account. Installing this version therefore requires an existing dashboard browser session to sign in again. Replacement sessions remain valid when their original signing configuration is restored.


## Behavior change: native execution requires runner opt-in

Upgraded native servers serve their queue without an in-process agent executor. Owners explicitly enroll and install a runner on this machine or another to continue processing queued agent work. Startup, the server-host doctor and the dashboard make this choice visible. Existing standalone legacy services retain their membership and capture while the owner completes an explicit handover.

The owner/admin-only `GET /api/workers/legacy` route is the declared legacy-inventory API contract. The dashboard reads the same fleet projection through `/api/status`, splitting its rows by credential class; it creates no second inventory. Members see only their own machines in that projection.

Machine execution URL locks use one key per origin, including all path prefixes. `0.0.0.0`, `localhost`, IPv4 loopback and IPv6 loopback share a key; authenticated Deployment identity serializes other origins.
